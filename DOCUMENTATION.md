**Версия:** 1.70.3
**Автор:** Кнап Руслан Юрьевич
**Дата:** 2026-08-27 (комплексная стабилизация CLI, данных, Telegram и браузерных карт)
**Лицензия:** Proprietary (все права принадлежат автору)

## О проекте

**mem-tool** — это консольная утилита для работы с векторной базой знаний. Она позволяет сохранять текстовые заметки, факты и документы, а затем искать их не по точному совпадению слов, а **по смыслу** (семантический поиск).

### Текущий релиз 1.70.3

Комплексно устранены ошибки, найденные при полном code review и проверке
реальных пользовательских сценариев. История документов теперь адресует каждый
снимок собственным `dhs-*` ID: разные схемы разбиения одной content-revision и
соответствующие состояния knowledge graph больше не схлопываются. Старые таблицы
истории мигрируют один раз без разрушительного DDL. Пустой повторно
проиндексированный файл получает явное текущее empty-состояние: прежний текст
сразу исчезает из поиска, но остаётся доступен для `map restore` и точного
rollback. Переходы empty → non-empty и работа нескольких процессов также
сохраняют историю и обновляют локальный кэш.

Замена, опустошение и восстановление документа сверяют долговечное поколение
таблицы entries. При внешнем изменении полный cache snapshot загружается в
отдельной read-only транзакции; при совпадении поколения в памяти применяется
только delta выбранного источника. Поэтому пакетная индексация больше не
декодирует весь корпус с embeddings внутри каждой SQLite writer transaction.
Поиск, статистика, списки источников, evidence-подбор и corpus diff также
проверяют поколение перед чтением, поэтому долгоживущий второй процесс не
показывает удалённые или заменённые chunks. Все provenance-чувствительные
изменения повторно разрешают anchors по строкам из той же SQLite-транзакции и
fail-closed отклоняют evidence, изменившееся в другом процессе.

CLI теперь до смены каталога, создания `.mem` и открытия SQLite строго
проверяет глобальные флаги, отсутствующий `--dir`, все команды с
автосозданием (`add`, `add-file`, `import`, `index`, `config`) и простые команды
с фиксированной арностью (`init`, `version`, `help`, `stats`, `sources`,
`repl`, `where/current`, `source`, `show/get/view`). Сложные команды
`search`, `ask`, `map` и `mindmap` сохраняют собственную проверку внутри
обработчиков.
`--color=auto` поддерживается, а `--` завершает разбор флагов без потери
литерального хвоста запроса. Read-only команды `mem-index`, включая `find`, не
создают пустую БД в частично инициализированном каталоге. REPL не записывает
секрет Polza и при старте атомарно удаляет такие команды из старой истории;
slash-команды понимают кавычки, пустые аргументы и экранирование пробела или
кавычки; обычные обратные слэши, UNC-пути и завершающий `\` сохраняются
буквально, а незакрытая кавычка отклоняется без выполнения команды.

Telegram-бот принимает только private chats, безопасно обрабатывает updates без
message и по умолчанию не запускается без allowlist. Публичный режим требует
явного `MEM_BOT_ALLOW_PUBLIC=true`, положительных per-user/global rate limits,
квот записей и числа пользователей. Внешним пользователям больше не выдаются
сырые provider/SQLite ошибки и локальные пути. Долгих embedding-операций может
быть не больше двух одновременно и одной на пользователя; уже выполняющееся
или конкурирующее открытие личной базы также сразу возвращает просьбу повторить
запрос, поэтому быстрые команды не блокируются всем worker-пулом. Квота записей
проверяется непосредственно в SQLite и при ошибке чтения запрещает запись.
Повтор отправки без Markdown выполняется
только для подтверждённой Telegram-ошибки разбора entities, но не для 429,
тайм-аута, отмены или неоднозначной сетевой ошибки.

В браузерных картах активные HTML/SVG-источники отдаются только как attachment с
жёстким CSP; пути source-add нормализуются, ошибки не раскрывают локальную
систему, фоновые AI jobs завершаются до закрытия Store. Knowledge graph получил
responsive layout для промежуточных и мобильных ширин, конечную стабилизацию
force-layout, доступную клавиатурную навигацию и modal focus trap. Классическая
карта использует индексированные lookup вместо рекурсивных обходов; новые
ограничения узлов/глубины применяются к ручным и AI-изменениям, а legacy-карта
за пределами безопасного renderer получает явное предупреждение без изменения
данных. Её заголовок переносится без горизонтальной прокрутки на промежуточной
ширине, а ревизия в расширенной работе синхронизируется после правки, undo и
redo. Ввод/вывод FB2, EPUB, embeddings и внешних PDF/DjVu extractors ограничен
по размеру и времени. Конфиг сохраняется атомарной заменой, а прерванная первая
запись `config.json` или `meta.json` полностью очищает незавершённый каталог.

Добавлены регрессионные тесты для межпроцессной истории, snapshot selector,
empty restore/rollback, конкурентной инициализации, строгого CLI, UNC-путей и
миграции REPL, межпроцессных read/write provenance-проверок, согласованности
FTS, атомарного `important`, Telegram admission/rate limits, fail-closed квоты и
безопасного fallback, bounded extractors, AI JSON fallback и
desktop/mobile браузерных контрактов.

### Релиз 1.70.2

Исправлено создание новой классической карты через AI Studio с областью
«Вся активная база / без фильтра». Интерфейс показывал этот вариант как
выбранный, но пустой набор фильтров backend ошибочно трактовал как отсутствие
evidence, поэтому модель не запускалась и пользователь получал сообщение об
отсутствии актуальных фрагментов.

Теперь пустой grounded-scope действительно закрепляет все current versioned
chunks активной локальной базы. То же правило применяется, если пользователь
явно отключил наследование источников ветви или ищет источники по всей базе.
Явный режим модельной заготовки без локальных источников остаётся полностью
отдельным и не получает содержимое базы.

Без заданного лимита сохраняется безопасный порог 512 фрагментов: более крупная
область не обрезается молча и не отправляется модели, а выдаёт русскую подсказку
сузить документ, страницы или поиск либо указать осознанный лимит в
дополнительных настройках. Core- и HTTP-тесты воспроизводят точный запрос из AI
Studio и подтверждают, что preview получает всю активную базу.

### Релиз 1.70.1

Исправлено расширение ветви и заполнение узла в AI Studio классических карт.
Раньше режим «Использовать источники» смотрел только на прямые evidence-ссылки
выбранного узла. Структурный или вручную созданный узел без собственной ссылки
останавливал операцию, даже когда актуальные источники уже были привязаны ниже
в этой ветви либо у ближайшего родительского узла.

Теперь помощник сначала собирает только current versioned evidence выбранного
поддерева, а если его там нет — поднимается к первому ближайшему родителю с
актуальными источниками. Соседние ветви и вся карта автоматически в область не
добавляются. Ссылка узла классической карты на объект расширенной knowledge map
тоже раскрывается в его точные evidence anchors. Устаревшие anchors не передаются модели, а отсутствие материала
объясняется пользователю по-русски с конкретными способами выбрать документ,
страницы или точные фрагменты. Модель и карта по-прежнему разделены обязательным
предпросмотром и явной публикацией.

Тесты покрывают наследование evidence от дочернего узла, ближайшего предка и
связанного объекта knowledge map, отсутствие вызова модели при пустой области и
отсутствие внутренних терминов API в пользовательской ошибке.

### Релиз 1.70.0

Второй пользовательский срез фоновых jobs переводит генерацию учебных карточек
и открытых вопросов в `mem map open` с одного долгого HTTP-запроса на отдельную
bounded-задачу. Учебный контур показывает позицию в очереди, фазу, процент,
число обработанных evidence/кандидатов и прошедшее время; та же кнопка во время
работы становится явной командой «ОТМЕНИТЬ ГЕНЕРАЦИЮ».

На один live-server работает один worker генерации и ожидают не более четырёх
заданий. Переполнение получает 429 с `Retry-After`. Состояния
`queued/running/completed/failed/cancelled`, compact status и готовый preview
разделены: polling не передаёт тексты всех кандидатов, а полный результат
запрашивается только после строгой проверки. Terminal jobs и preview хранятся
не более десяти минут и ограничены двенадцатью записями.

Прогресс проводится через реальные безопасные границы: проверка запроса,
закрепление выбранной области, вызов модели, строгая проверка JSON и цитат,
исправляющий повтор и повторная проверка manifest/evidence перед записью preview.
Отмена ожидающей задачи мгновенна; активная передаёт context провайдеру. Если
атомарная запись preview уже успела завершиться, успешный durable результат
побеждает позднюю отмену и не становится скрытым run.

Модель по-прежнему ничего не публикует в knowledge graph. Готовые варианты
отображаются как preview с точными документом, страницей и блоком; пользователь
сам выбирает варианты и отдельным действием сохраняет их только как draft.
Изменение выбора или evidence приводит к `changed`, а не к сохранению устаревших
кандидатов. Старый синхронный endpoint оставлен для совместимости, но штатный
интерфейс использует `start/status/cancel/result`.

Тесты покрывают очередь и её границу, прогресс, отмену queued/running, отсутствие
результата после отмены, HTTP-auth, получение preview, context cancellation,
строгую JavaScript-синтаксическую проверку и прежний синхронный API. Следующий
срез — переносимый backup пользовательских views и дальнейшая унификация
длительных live-операций.

### Релиз 1.69.0

Начат первый пользовательский срез фоновых jobs этапа 9. Полный экспорт
расширенной knowledge map из `mem map open` больше не удерживает один длинный
HTTP-запрос: диалог создаёт серверное задание, показывает очередь, текущую фазу,
процент, число проверенных уникальных evidence coordinates и прошедшее время,
а готовый файл скачивает отдельным защищённым запросом.

На один live-server работает один worker и не более четырёх ожидающих заданий.
Это ограничивает одновременную нагрузку на SQLite и память; переполненная очередь
возвращает 429 с `Retry-After`, а не запускает неограниченные goroutines. Готовые
артефакты суммарно занимают не более 128 MiB, после скачивания освобождаются
сразу, без скачивания хранятся не более десяти минут. В очереди сохраняется
только закреплённый запрос, но не копия всей карты.

Кнопка «ОТМЕНИТЬ» удаляет ожидающую работу либо посылает cooperative cancellation
активному worker. Контекст проверяется до/после чтения снимка, между пакетами
evidence и перед публикацией результата; цельная фаза рендера не прерывается
посередине, но её байты отбрасываются, если отмена пришла до публикации. При
остановке `mem map open` все queued/running jobs отменяются, частичный файл
никогда не становится доступным.

API start/status/cancel/download по-прежнему доступно только на loopback, требует
same-origin, Fetch Metadata и одноразовую session capability. Content/state pins
повторно проверяются внутри worker; изменившаяся карта завершает job понятным
`changed`, а не выдаёт файл из смешанного снимка. Прежний синхронный `/api/export`
оставлен для обратной совместимости, CLI `mem map export` не изменён.

Тесты покрывают успешный lifecycle, реальный HTTP download, прогресс, границу
очереди, отмену queued/running, terminal conflict, контекст остановки и валидный
JavaScript диалога. Следующий срез — распространить тот же bounded-job контракт
на другие долгие live-операции и добавить переносимый backup пользовательских
views.

### Релиз 1.68.1

Первый измеренный цикл оптимизации устраняет две N+1-последовательности в
knowledge map. Загрузка полного графа теперь читает узлы, связи и обе таблицы
evidence четырьмя SQL-запросами независимо от числа объектов, сохраняя порядок
якорей. Разрешение current/stale/missing группирует одинаковые координаты и
читает уникальные позиции пакетами не более 200, вместо отдельного запроса на
каждый повторяющийся anchor.

Live-view больше не строит review повторной загрузкой графа: обзор, revision
diff и portable-export pin используют один уже проверенный SQLite-снимок. Это
одновременно ускоряет открытие и исключает расхождение, когда review и
отрисовываемый граф могли относиться к двум соседним состояниям. Публичный
`ReviewKnowledgeGraph` теперь также разрешает evidence непосредственно в
read-only SQLite-снимке и видит замену документа другим процессом, а не
устаревший in-memory cache.

На контрольной карте 1000 узлов / 999 связей с одним повторяющимся evidence
локальный benchmark загрузки на машине разработки снизился с 195,9 до 20,8 мс
(примерно 9,4 раза). Это не универсальная гарантия скорости: точный эффект
зависит от диска, корпуса и числа уникальных координат. Для своей базы его нужно
проверять той же `mem map profile` при совпадающих digests.

Регрессии закрыты тестами постоянного числа SQL-запросов, пакетной границы,
сохранения current/stale/missing, внешней замены документа и benchmark на 1000
узлах. Формат базы, CLI и экспортных артефактов не изменён, поэтому выпуск
оформлен как обратно совместимое исправление производительности 1.68.1.

Следующий шаг этапа 9 — вынести действительно длительные операции в фоновые
jobs с очередью, отменой и наблюдаемым прогрессом, затем добавить переносимый
backup пользовательских views.

### Релиз 1.68.0

Третий срез этапа измеримого качества добавляет read-only команду
`mem map profile [-iterations N] [--view <имя>] [--json]`. Она измеряет четыре
реальных стадии host-side пути live-карты: загрузку полного графа и evidence из
SQLite, построение content/state-pinned снимка, сборку данных выбранного view и
сериализацию автономного HTML. Для каждой стадии сохраняются все nanosecond
samples, min, median, p95, max и mean.

Отчёт одновременно фиксирует размеры `store.db`, WAL/SHM, SQLite page/freelist,
число entries/документов, узлов/связей/evidence, размер и SHA-256 HTML, среду
GOOS/GOARCH/Go/CPU и точные graph/evidence/view digests. Если граф, evidence,
review/layout или другой видимый state меняется во время серии, смешанный
результат отклоняется вместо публикации ложных timings. Команда не вызывает
модель и не изменяет базу.

Профиль сознательно не выдаёт серверную сериализацию за скорость браузера:
JavaScript execution, layout, paint, GPU, FPS и интерактивная задержка явно
указаны как неизмеренные. Перед серией строится проверочный pin, поэтому это
прогретый рабочий путь, а не cold-start процесса. Сравнивать timings следует на
одном компьютере, при одинаковом числе итераций и совпадающих snapshot digests.

Следующий шаг этапа 9 — использовать собранные профили для адресной оптимизации,
затем вынести тяжёлые операции в фоновые jobs и добавить переносимый backup
пользовательских views.

### Релиз 1.67.0

Второй срез этапа измеримого качества добавляет read-only команду
`mem map eval-labeled <manifest.json> [--json]`. Она сравнивает current claims и
связи `contradicts` с подготовленным человеком эталоном и детерминированно
считает TP/FP/FN, precision, recall и F1 отдельно для утверждений и
противоречий. Это позволяет измерять не только объём покрытия, но и фактическую
полноту извлечения и число ложных выводов.

Manifest версии 1 задаёт область документа/страниц/тега, оцениваемые статусы,
порог текстового совпадения, ожидаемые claims, пары противоречий и обязательные
пороги качества. Claim можно закрепить не только текстом и алиасами, но и точным
`node_id` либо списком допустимых `citation_id`. Сопоставление использует
нормализованный token Dice, не embeddings и не языковую модель. Противоречие
засчитывается только как реальная связь `contradicts` между двумя уже
сопоставленными claims; дубли и связи с неожиданными концами становятся false
positive.

В оценку входят только объекты с current evidence внутри выбранной области.
Stale/missing объекты не исчезают молча: отчёт показывает число исключённых.
Human-отчёт перечисляет лишние и пропущенные объекты с понятным файлом и
страницей, JSON сохраняет полные структурированные детали. Manifest, граф,
состояние evidence и итоговый снимок имеют отдельные SHA-256 digests. Проверка
строится в одной SQLite read-транзакции, не вызывает модель, не меняет базу и при
непройденном gate возвращает код 1 после печати полного отчёта.

Следующий шаг этапа 9 — измеренный профиль SQLite и браузерного рендера на
больших картах; затем фоновые jobs и переносимый backup пользовательских views.

### Релиз 1.66.0

Начат этап измеримого масштабирования и качества. Новая read-only команда
`mem map eval <manifest.json> [--json]` применяет строгий воспроизводимый
quality gate к текущему coverage-снимку карты. Manifest версии 1 задаёт область
документа/страниц/тега и явные требования к полноте импорта, обработке и
покрытию, количеству непокрытых chunks, low-confidence OCR, предупреждениям,
узлам/связям и состояниям draft/stale/missing.

Проверка не вызывает embedding или answer-модель и не изменяет базу. Отчёт
содержит стабильные manifest/snapshot digests и упорядоченный список фактических
значений. Непройденный gate всё равно печатает полный human либо JSON-отчёт, но
завершает процесс с кодом 1, поэтому его можно использовать в PowerShell, CI и
при повторной проверке одного корпуса после изменения настроек. Manifest
ограничен 1 MiB, неизвестные поля, лишний JSON, неверные диапазоны и отрицательные
пороги отклоняются до чтения карты.

Это первый срез этапа 9: он фиксирует измеримый baseline до оптимизации. Следом
идут размеченные precision/recall-наборы для claims/contradictions, профиль
SQLite/рендера на больших картах и переносимый backup пользовательских views.

### Релиз 1.65.0

Расширенную knowledge map теперь можно экспортировать целиком в семь
переносимых форматов: `markdown`, `outline`, `opml`, `graphml`, `gexf`,
`mermaid` и `obsidian`. Старое поведение `mem map export` без флагов сохранено:
оно по-прежнему выводит JSON графа в stdout. Для файлового экспорта используются
`--format`, `--output`, необязательный `--title` и явный `--force`.

Экспорт всегда охватывает полный текущий граф, а не только видимую раскладку,
фильтр или выбранную область. GraphML и GEXF сохраняют направленные
типизированные связи для Gephi/yEd и других графовых инструментов; Mermaid
создаёт `flowchart`; Markdown и Obsidian дают читаемый справочник; outline и
OPML подходят для планов и обмена с outline-приложениями. Все форматы включают
canonical Base64-envelope с точными узлами, связями, evidence anchors и
разрешённым состоянием каждого источника.

Операция закрепляет отдельные content digest и source-state digest. Снимок
строится в одной SQLite read-транзакции и видит изменения, сделанные другим
процессом, поэтому устаревшая live-страница получает conflict вместо незаметно
изменившегося файла. `stale` и `missing` источники не удаляются из результата, а
остаются явно видимыми. CLI по умолчанию не перезаписывает существующий файл,
атомарно заменяет его только с `--force` и защищает активный `store.db` вместе с
SQLite sidecar-файлами.

Один артефакт ограничен 10 000 узлов, 100 000 связей и 128 MiB. Проверка
выполняется до замены файла, поэтому ошибка размера не повреждает существующий
результат.

В `mem map open` команда «ЕЩЁ → ЭКСПОРТ КАРТЫ» открывает отдельный спокойный
диалог, показывает полный объём графа и счётчики current/stale/missing, поясняет
назначение форматов и передаёт готовые байты браузеру. Путь локального файла не
отправляется серверу. Экспорт выбранной области в отчёт/план/CSV/JSON остаётся
отдельной операцией в рабочем пространстве «АНАЛИЗ».

### Релиз 1.64.0

Классическая карта получила отдельное рабочее пространство «Расширенная
работа», которое не перегружает компактный инспектор узла. В нём можно задать
grounded-вопрос по выбранной ветви, собрать учебный набор, сравнить две карты и
создать новую ручную карту из одного из пяти встроенных шаблонов. Те же
операции доступны в CLI и TUI командами `mindmap ask-branch`, `templates`,
`template-create`, `compare` и `study`.

Вопрос по ветви закрепляет ревизию, content digest, state digest, состав
поддерева и все current versioned evidence. Answer-модель получает только эти
проверяемые фрагменты; ответ проходит прежнюю строгую валидацию citations и
показывает имя документа, физическую страницу, блок и фрагмент. Ветка и история
карты при этом не меняются. Учебный набор формируется без модели из уже
сохранённых заголовков, summary/body и источников и скачивается как подробный
Markdown.

Сравнение двух карт полностью локально сопоставляет структурные пути и
содержимое узлов и отдельно показывает добавленные, удалённые, изменённые,
перемещённые и неизменившиеся элементы. Шаблоны «Мозговой штурм», «Изучение
темы», «Принятие решения», «План проекта» и «Разбор документа» создают только
пустую ручную структуру, не вызывают модель и не выдают заготовки за факты.

Переносимый экспорт расширен форматами `markdown`, `mermaid` и `obsidian`.
Markdown сохраняет полный читаемый outline и понятные источники; Mermaid — код
`mindmap` для документации; Obsidian — одну заметку с front matter,
Mermaid-схемой, block ID и полным содержанием. Во всех трёх форматах canonical
provenance встроен как Base64-envelope, а экспорт по-прежнему закреплён
revision + content digest + source-state digest.

### Релиз 1.63.0

Классическую карту теперь можно выгрузить целиком одной командой
`mem mindmap export` в автономный интерактивный HTML, векторный SVG, растровый PNG, полный
JSON или иерархический OPML. Экспорт строится из текущей закреплённой ревизии,
content digest и state digest источников и
всегда включает всё дерево независимо от свёрнутых в браузере ветвей. Модель не
вызывается, карта и её история не меняются.

HTML полностью самодостаточен: поиск, раскрытие ветвей, светлая/тёмная тема,
тексты узлов и проверяемые источники работают без сервера и Интернета. JSON
сохраняет полный документ карты; SVG несёт provenance-метаданные; OPML хранит
иерархию, заметки, типы и сериализованные источники в namespace `mem`. PNG
показывает revision и digest в заголовке и дополнительно хранит полный
provenance JSON в стандартном `iTXt`-блоке `mem-provenance`. SVG и PNG содержат
всё дерево, хотя очень длинные подписи могут быть укорочены внутри видимой
карточки; полный текст остаётся в tooltip/embedded provenance. OPML сохраняет
точные поля `mem` в Base64; обратный импорт OPML в mem-tool пока не реализован.

В `mem mindmap open` над картой находится кнопка «⇩ Экспорт». Она открывает
отдельный диалог с описанием пяти форматов, полным числом узлов/источников и
предупреждением о локальных путях и выдержках. Браузер получает только готовые
байты и сам предлагает место сохранения; путь назначения никогда не передаётся
live-серверу.

Формат и выходной путь обязательны. По умолчанию файл создаётся только как
новый через exclusive create; существующий результат остаётся нетронутым.
Явный `--force` сначала полностью записывает временный файл в том же каталоге и
только затем заменяет назначение. CLI дополнительно запрещает использовать
активный `store.db` и его `-wal/-shm/-journal` как путь результата. Host-side лимиты — до 10000 узлов,
16 MiB входного документа карты и 128 MiB готового артефакта. Для PNG действует
более строгий безопасный предел: до 512 узлов, 12000×12000 и 24 млн пикселей;
для более крупной карты следует выбрать масштабируемый SVG или HTML.

Одновременно усилена граница доверия веб-источников классической карты:
сохраняются и открываются только абсолютные `http`/`https` URL без встроенных
учётных данных. Небезопасные схемы и относительные адреса отклоняются до новой
ревизии; live-интерфейс повторяет allowlist для защиты старых записей.

### Релиз 1.62.0

Классические карты получили отдельного AI-помощника с обязательным
предпросмотром. Он создаёт новую карту, расширяет выбранную ветвь, дополняет
узел или предлагает источники, но никогда не записывает ответ модели прямо в
рабочее дерево. Сначала mem-tool закрепляет запрос, ревизию карты и точные
versioned chunks, разбивает большой материал на контролируемые пакеты и
принимает от модели только один строго проверяемый JSON-объект.

Каждое предложение хранится отдельно от карты и показывает будущие узлы,
текстовые изменения и человекочитаемые источники. Можно снять отдельные пункты;
дочерний узел нельзя опубликовать без родителя. Перед публикацией сервер снова
проверяет ревизию карты, блокировку узла и актуальность document/revision/chunk
anchors. Новая карта появляется только после подтверждения, а изменения
существующей карты фиксируются одной ревизией и одной append-only записью,
поэтому полностью отменяются обычным undo.

Для крупных документов используется отдельный map-reduce-план с сохранёнными
проверенными пакетами. Ошибка модели, отмена, превышение лимита, неправильный
родитель или придуманная citation не оставляют частичного дерева. Локальные
модели получают JSON Schema; для несовместимых моделей действует ограниченное
увеличение output budget и исправляющие повторы, но непроверенный свободный
текст не принимается.

В браузере AI вынесен в широкую Studio «Настройка → Обработка → Предпросмотр»,
а не добавлен ещё одной перегруженной вкладкой инспектора. Те же операции
доступны из CLI/TUI и всегда разделены на создание preview и явное применение.
Режим без документов разрешается только как явно отмеченная непроверенная
модельная заготовка; документный режим требует точных локальных источников.

### Релиз 1.61.0

Вкладка «Источники» классической карты стала полноценным рабочим местом. Без
вызова модели она ищет текст по всем current-chunks активной `.mem`-базы,
фильтрует результаты по документу и физической странице и показывает
человекочитаемые координаты и выдержку до привязки. Клиент передаёт только ID
выбранной записи; сервер сам строит строгий document/revision/chunk/evidence
anchor из актуального полного текста, поэтому браузер не может подменить цитату.

К одному узлу теперь можно привязать четыре явно различающихся типа источников:
точный фрагмент базы, локальный файл, веб-ссылку и существующий узел сложного
knowledge graph. Файл либо связывается по абсолютному пути, либо копируется из
браузера в приватный каталог `.mem/mindmap-files`; лимит импорта — 64 MiB,
существующие файлы никогда не перезаписываются. Веб-ссылка принимается только с
абсолютной схемой `http`/`https`, а knowledge node повторно проверяется в SQLite.

Карточки источников показывают состояние `current`, `stale` или `missing`, точный
путь, страницу/блок/chunk и выдержку. Current PDF открывается в новой вкладке на
физической странице; локальные файлы выдаются только через same-origin
capability-cookie и не выбираются по пути из URL. Источник можно скопировать,
переставить или отвязать без удаления исходного документа. Все эти действия
повышают ревизию карты, входят в append-only историю и поддерживают undo/redo.

CLI/TUI получили те же операции: расширенный `mindmap source-add`, а также
`source-remove` и `source-move`. Браузерное приложение остаётся loopback-only и
не отправляет запросы во внешнюю сеть. AI-помощник с preview и атомарной
публикацией добавлен в 1.62.0.

### Релиз 1.60.0

Команда `mem mindmap open` открывает отдельное локальное приложение классических
карт мыслей. Первый экран — библиотека независимых карт с поиском, созданием,
редактированием названия/описания, независимым копированием, архивом и
восстановлением. Второй экран — спокойное left-to-right дерево: постоянно видны
только parent-child линии, все узлы подписаны, ветви раскрываются по требованию.

Редактор поддерживает полнотекстовый поиск по узлам, ограничение глубины,
раскрытие/сворачивание всей карты, масштаб и вписывание, светлую/тёмную тему,
добавление дочернего или соседнего узла, изменение типа/summary/Markdown-текста,
закрепление, перенос через форму или drag-and-drop с проверкой циклов и два
режима безопасного удаления. Справа находятся отдельные вкладки содержания,
понятных источников и append-only истории. Из истории доступны snapshot, undo и
redo; все записи по-прежнему проходят через optimistic revision pin.

Приложение не загружает внешние шрифты, скрипты или стили и работает без
Интернета. HTTP-сервер слушает только `127.0.0.1`; каждый запрос к данным требует
same-origin и одноразовый session token процесса. Браузерная проверка релиза
прошла на изолированной базе через реальные действия пользователя. Управление
источниками добавлено следующим релизом 1.61.0.

### Релиз 1.59.0

Начата отдельная линия классических карт мыслей, не смешанная с существующим
аналитическим knowledge graph. Новая команда `mem mindmap` управляет библиотекой
независимых упорядоченных деревьев: можно создать пустую карту, показать её,
добавить, переименовать и переместить узел, удалить целую ветвь либо только узел
с переносом дочерних элементов, закрепить узел, привязать точный фрагмент
документа, посмотреть историю, создать контрольную точку и выполнить undo.

Обычная работа выполняется по понятным названиям карты и узла. Внутренние ID
остаются в JSON для интеграций, но не требуются в человекочитаемом CLI/TUI.
Каждое изменение атомарно повышает ревизию карты и добавляет полные before/after
снимки в защищённый от UPDATE/DELETE журнал. Флаг `--expect N` обеспечивает
optimistic concurrency: устаревшая вкладка или скрипт не перезапишет более новую
ревизию. Последовательные undo также являются новыми append-only изменениями,
поэтому история не переписывается.

Схема уже едина для ручных, сгенерированных и гибридных карт. Импорт полного
результата генератора проверяет один корень, всех родителей, отсутствие циклов,
типы и размеры полей до транзакции; при ошибке карта не публикуется частично.
Evidence-источник принимается только пока его точный document/revision/chunk и
excerpt имеют состояние `current`; после повторного импорта просмотр честно
показывает `stale` или `missing`. Эта модель стала основой браузерного редактора
1.60.0; генерация по запросу/документу подключается отдельным следующим этапом.

### Релиз 1.58.0

Исторический снимок теперь можно безопасно восстановить. Команда `mem map restore`
без `--confirm` всегда выполняет только read-only preview: показывает переход
ревизий, полный chunk-diff, размеры текущей и целевой карты, предупреждение о
полной замене knowledge graph и вычисляет `sha256` plan digest. Digest привязан к
хешам всех текущих/целевых chunks и обеих карт; любая правка после preview делает
план недействительным.

Только повтор команды с точным `--confirm <plan-digest>` запускает одну SQLite-
транзакцию. Перед заменой сохраняются текущий корпус и точный content-addressed
снимок карты, затем восстанавливаются полный текст, embedding-векторы,
provenance и граф выбранного момента. Ошибка на любом шаге откатывает всё.
Append-only журналы review/edit/learning/import и именованные визуальные виды не
удаляются.

Каждое применение записывается в неизменяемый `knowledge_restore_runs` и выдаёт
`restore-run-*`. `mem map restore --rollback <run-id>` сначала строит новый
state-pinned preview, а после отдельного подтверждения возвращает корпус и именно
тот граф, который существовал непосредственно перед исходной операцией. История
доступна через `mem map restore-runs [--json] [-limit N]`. Модель не вызывается.

### Релиз 1.57.0

Перед атомарной заменой versioned-документа mem теперь сохраняет прежнюю ревизию
в неизменяемой истории: полный текст, координаты, хеши, embedding provenance и
векторы каждого chunk. В той же транзакции фиксируется content-addressed снимок
карты. Если архивирование или импорт завершается ошибкой, ни рабочий документ,
ни история не меняются. Повторное сохранение той же ревизии не создаёт дубликат.

`mem map snapshots [--document <путь|document-id>] [--json]` перечисляет доступные
снимки. `mem map corpus-diff --document <путь|document-id> [--from <revision>]
[--to <revision|current>] [--json]` сравнивает весь сохранённый набор chunks без
модели и показывает добавленные, изменённые, исчезнувшие и неизменившиеся
фрагменты. Обычный `mem map diff` автоматически добавляет сводку полного
chunk-diff, когда история документа уже существует.

История начинает накапливаться с 1.57.0 при первой фактической замене ревизии;
текущая единственная ревизия намеренно не дублируется в SQLite. Снимки уже содержат
все данные для точного восстановления. Изменяющая команда с обязательным preview
и проверяемым rollback добавлена в 1.58.0.

### Релиз 1.56.0

В live-карте появилось отдельное рабочее пространство «ИЗМЕНЕНИЯ». Оно локально,
без модели сравнивает immutable evidence-снимки узлов и связей с текущими
versioned chunks активной базы. Для каждого документа видны прежняя и текущая
ревизии, изменённые или исчезнувшие координаты, число затронутых узлов/связей и
сравнение «Было в карте → Текущий chunk». Из строки объекта можно сразу открыть
обычный инспектор и проверить все его источники.

Фильтры отделяют документы, требующие внимания, изменённые источники,
исчезнувшие фрагменты и полностью актуальные документы. Поиск работает по пути,
document ID, названиям и типам объектов. Новый CLI-эквивалент
`mem map diff [--document <путь|document-id>] [--json]` доступен также через
меню команд TUI.

Отчёт намеренно не выдаётся за полный построчный diff старого файла: Store
сохраняет полный текст только текущих chunks, а от прежней ревизии карта хранит
точные cited excerpts. Поэтому достоверно классифицируются текущие, изменённые и
исчезнувшие evidence и их влияние на карту; неизвестные старые chunks не
объявляются «добавленными» или «удалёнными» без исторического снимка корпуса.

### Релиз 1.55.0

Готовый подтверждённый учебный маршрут теперь экспортируется из отдельного
сворачиваемого блока режима «ОБУЧЕНИЕ». Доступны три локально формируемых
формата: UTF-8 TSV для импорта в Anki, подробный Markdown-справочник и CSV с
текущим расписанием. В экспорт попадают только `active`-карточки и вопросы с
актуальными evidence, повторно проверенные по manifest и route digest.

Anki-файл содержит стандартные заголовки `separator`, `html`, `deck`, `columns`
и `tags column`; первые поля совместимы с обычной карточкой Front/Back. На
обороте сохраняются ответ, понятные координаты источника и справочное состояние
расписания mem-tool. Невидимый стабильный ID в Front предотвращает склейку
разных карточек с одинаковым вопросом при duplicate detection. CSV отдельно
передаёт due date, интервал, ease, число
успешных повторений, lapses, последнюю оценку и число попыток; Markdown группирует
материал по этапам prerequisite-маршрута.

Текстовый импорт Anki намеренно не выдаётся за перенос native scheduling:
планировщик Anki начинает собственную историю после импорта. Для переноса
внутреннего Anki scheduling требуется пакет `.apkg`, которого этот релиз не
создаёт. Экспорт read-only, не вызывает модель и не меняет расписание mem-tool.

### Релиз 1.54.0

Большая графовая карта получила автоматические уровни детализации. На дальнем
масштабе показываются детерминированно выбранные опорные узлы крупнейших
кластеров, затем темы, знания и полный набор деталей. Активный фокус, поиск,

семантического масштаба. Режим можно отключить командой «Показать все узлы».

Ручные фильтры типов связей продолжают действовать и не заменяются линзой.

### Релиз 1.50.0

Проверенный учебный маршрут теперь можно превратить в реальную сессию

ПОВТОРЕНИЕ»: live-карта отберёт только новые карточки и те, чей срок уже

историю. Текущее расписание хранится отдельно как восстанавливаемая проекция.

переносится на новую ревизию карточки. Автономный HTML остаётся read-only;
учебные записи разрешены только same-origin API защищённой live-карты.

### Релиз 1.49.0

В выбранной области live-карты теперь можно нажать «ПОСТРОИТЬ УЧЕБНЫЙ
МАРШРУТ». Сервер без вызова модели находит связанные с выбором карточки и
открытые вопросы, но допускает в маршрут только объекты `active` с непустыми

от зависимого объекта к его предпосылке. Результат разбит на этапы, у каждого
вопроса видны ожидаемый ответ, документ, физическая страница и блок. Щелчок по

предупреждения. Операция read-only, повторно проверяет manifest и доступна

### Релиз 1.48.0

В живой карте появился первый срез учебного рабочего пространства. Выберите
один или несколько узлов с актуальным evidence, при необходимости задайте
учебный акцент и количество кандидатов, затем нажмите «СОЗДАТЬ УЧЕБНЫЕ
КАНДИДАТЫ». Answer-модель предложит карточки и открытые вопросы, а интерфейс до
сохранения покажет формулировку, ожидаемый ответ и понятные координаты каждого
источника.

Генерация строго ограничена закреплённым manifest: модель не получает скрытый
контекст из остальной базы, обязана вернуть структурированный JSON и сослаться
на реально переданные evidence refs. Неверный ответ получает один исправляющий
повтор, после чего отклоняется без записи в карту. Для локальных моделей
используется JSON Schema; облачные Ollama-модели сохраняют совместимый
prompt-only контракт.

Пользователь сам отмечает подходящие варианты и сохраняет их только как
`draft`, указав автора. Одна транзакция создаёт generated-карточки/вопросы,
копирует точные anchors и связывает их со всеми исходными узлами через
`derived_from` или `asks`. Immutable run и append-only запись сохранения
фиксируют manifest, модель, generation digest и выбранные варианты. Если после
предпросмотра изменился объект, источник или ревизия документа, запись
блокируется. Черновики не считаются изученным либо подтверждённым знанием до
ручной проверки.

### Релиз 1.47.0

Живая карта теперь экспортирует точно закреплённую выбранную область в пять
форматов: переносимую JSON-ветвь, CSV-таблицу, Markdown-отчёт, план и чек-лист.
В правой панели выберите формат, при необходимости задайте понятное название и

### Релиз 1.46.0

В правой панели живой карты появилась команда «АНАЛИЗ ВЫБРАННОГО». Она без

### Релиз 1.44.0

### Релиз 1.43.3

Начат подэтап 3.3: PDF/DjVu теперь сохраняют versioned import manifest для
каждой выбранной физической страницы, в том числе когда страница не создала ни
одного chunk. Для страницы фиксируются понятный статус `stored`, `empty` или
`failed`, способ извлечения (`text`/`ocr`), объём текста, OCR confidence,
предупреждения, число блоков и chunks. Внутренние ID для обычной диагностики не
нужны:

```powershell
mem import-status
mem import-status --document "D:\Books\manual.pdf"
mem import-status --document "D:\Books\manual.pdf" --all-pages
mem import-status --json
```

По умолчанию команда подробно печатает только проблемные страницы; `--all-pages`
добавляет успешно сохранённые. Для документов, импортированных старой версией,
команда честно сообщает об отсутствии манифеста и предлагает повторный import —
номера пустых страниц по существующим chunks не выдумываются.

Манифест и новый набор embeddings записываются одной SQLite-транзакцией. Ошибка
записи манифеста откатывает замену chunks целиком. Ревизия PDF/DjVu теперь также
закрепляет физический page count и статусы страниц, поэтому изменение состава
пустых/непустых страниц делает старые evidence stale ожидаемым образом.

`mem map coverage` использует манифест как отдельный физический знаменатель:
показывает сохранённые, пустые и ошибочные страницы и их причины даже для
диапазона, где нет ни одного chunk. Graph coverage по-прежнему считается только
по versioned chunks и не смешивается с качеством импорта.

В этой версии page-local ошибка ещё останавливала весь import; ограничение снято
в 1.31.0.

### Релиз 1.29.0

Этап 3 продолжен командой `mem map extract`: она детерминированно выбирает только
текущие versioned chunks, которые ещё не процитированы картой и не зафиксированы
как обработанные завершённым extraction run. Область задаётся документом,
физическими страницами и/или тегом. `--dry-run` показывает объём без вызова модели:

```powershell
mem map extract "полный разбор документа" --document "D:\Books\manual.pdf" --dry-run
mem map extract "полный разбор документа" --document "D:\Books\manual.pdf" -batches 16
```

Полный текст каждого выбранного chunk обязан целиком помещаться в context budget;
тихое обрезание запрещено. Последовательный planner формирует до 128 пакетов,
а `-batches` ограничивает стоимость одного запуска (по умолчанию 8). Если chunks
остались, повтор той же команды после завершения создаёт следующий точный run и
берёт только необработанный остаток.

Перед первым обращением к модели создаются `knowledge_extraction_runs` и точные
batch-manifests. После каждого ответа сохраняется только строго проверенный граф
или явный `insufficient` checkpoint; сырой ответ модели не сохраняется. Ошибка
generation/JSON записывается как `failed`, карта не получает частичный batch.
Начиная с 1.43.1 достижение output-limit сначала вызывает до двух ограниченных
повторов того же пакета (4096 -> 8192 -> 16384); это не меняет настройки и не
перезапускает уже готовые checkpoints.
Продолжение выполняется командой с напечатанным ID:

```powershell
mem map extract "полный разбор документа" --document "D:\Books\manual.pdf" -batches 16 -resume ker-...
mem map extract-runs
mem map extract-run ker-...
```

`-resume` восстанавливает закреплённые citations, prompts, context и batch-limit.
Изменившаяся ревизия документа, другой фокус или параметры генерации отклоняются.
Карта обновляется только после терминальных checkpoints всех пакетов; финализация
идемпотентна. После неё каждый предъявленный модели chunk записывается в отдельный
ledger с исходом `extracted`, `processed` или `insufficient`. Изменившийся chunk
получает новую identity и снова становится кандидатом.

`map coverage` теперь отдельно показывает processing coverage и graph coverage.
Первое отвечает «сколько chunks уже предъявлялось контролируемому заданию», второе
— «сколько chunks реально процитировано узлами или связями». Это не смешивает
проверку модели с фактической полнотой карты. Отчёт также выводит физические
страницы и тексты import warnings, а не только их количество.

### Релиз 1.28.0

Начат этап 3 контролируемого извлечения. Новая команда `mem map coverage`
отделяет реальное измеримое покрытие исходного материала от обычного фокусного
поиска. Без фильтров она анализирует весь текущий versioned-корпус; область можно
ограничить точным путём/document ID, тегом и диапазоном физических страниц:

```powershell

mem map coverage --document "D:\Books\manual.pdf" --pages 20-45
mem map coverage --tag "Радиотехника" --json
```

Отчёт считает chunks с сохранённым текстом, страницы с текстом, полностью,

предупреждения импорта и evidence, ставшие `stale/missing`. Источник считается

подэтапа: resumable extraction jobs будут закреплять такой снимок и обрабатывать

не показывается.

Отчёт честно ограничивает знаменатель chunks, которые уже существуют в активной
базе. Пустую, не извлечённую или провалившуюся при импорте физическую страницу
невозможно восстановить только по таблице entries; это ограничение явно печатается
и сохраняется в JSON. Команда ничего не генерирует и не изменяет граф.

### Релиз 1.27.0

В живой карте теперь можно менять название узла или связи и описание узла без
ручного копирования внутренних ID и digest. Блок «РЕДАКТИРОВАНИЕ» показывает
текущий текст, автора и комментарий, сохраняет правку и позволяет отменить

upsert: повторное извлечение обновляет evidence, но сохраняет пользовательский
текст. После явной отмены правки будущая генерация снова может обновить его.

Endpoint `/api/edit` и `/api/edit/undo` доступны только в loopback workspace,
принимают один строгий JSON-объект, требуют same-origin, session capability и
ограничивают размер запроса. Изменение текста, возможный переход статуса и
append-only audit фиксируются одной SQLite-транзакцией.

### Релиз 1.26.0

Живая карта теперь поддерживает полный явный review-цикл без ручного копирования
внутренних ID и SHA-256 digest: `draft` можно подтвердить или отклонить, статус
`rejected` — вернуть в работу, а последнее допустимое решение — отменить. Статус
`resolved` больше не смешивается с отклонением: он по-прежнему означает объект,
закрытый другой операцией, например проверенным объединением дубликатов.

Для отклонения обязательна понятная причина. Возврат и отмена не переписывают
старую запись: каждый шаг добавляется в append-only `knowledge_reviews`, а undo
указывает точную запись, которую отменяет. Undo разрешён только для последнего
решения, при неизменившихся статусе и evidence. Подтверждение endpoint-узла нельзя
отменить, пока существуют активные связи: сначала нужно отменить подтверждение
этих связей. Так карта не создаёт скрыто некорректный граф.

Все четыре изменяющих endpoint (`approve`, `reject`, `reopen`, `undo`) доступны
только в loopback workspace, требуют строгий `POST application/json`, точный
same-origin, session capability и закреплённые evidence/review-состояния. Проверка,
смена статуса и новая audit-запись выполняются одной SQLite-транзакцией. Существующие
базы автоматически получают добавочную колонку связи undo с исходным решением;
исторические записи не изменяются. Автономный HTML остаётся read-only.

`текущее/всего`; для остальных команд выводятся предусмотренные обработчиком
стадии и результаты. Нижняя строка всегда показывает активную команду, прошедшее
время и количество полученных обновлений, а после выполнения остаётся итоговая
сводка по времени и числу сообщений. Даже команда без собственного подробного
прогресса получает общие отметки запуска и завершения.

Поток stdout и stderr объединён в том же порядке, в котором его читает TUI, и
продолжает безопасно дренироваться после `Esc`, не блокируя фоновый обработчик.
Проверка фиксирует, что первое сообщение появляется до завершения команды, а не
только наличие полного текста в её финальном результате.

### Релиз 1.19.1

`mem ask` теперь явно отключает reasoning/thinking в Ollama и запрашивает JSON

Неизвестные ссылки по-прежнему отклоняются; provenance, revision и evidence hash

Зачем это нужно?
- Вы работаете с AI-ассистентом (Claude, ChatGPT) и накапливаете факты, IP-адреса, команды, архитектурные решения
- Через месяц вы помните, что «там было что-то про сервер», но не помните точных слов


## Как создавался mem-tool

Проект создавался итеративно, от простого к сложному. Каждая версия добавляла новую возможность без поломки предыдущих.

### Версия 1.0 — Основа
Первая версия умела только три вещи:
- `mem add "текст"` — сохранить запись
- `mem search "запрос"` — найти по смыслу
- `mem recent` — показать последние

Текст превращался в вектор (эмбеддинг) через локальную модель **bge-m3** в Ollama, поиск работал по косинусной близости векторов. Хранилище — простой JSONL-файл (одна JSON-строка на запись).

**Почему JSONL?** Это append-only формат: новые записи добавляются в конец файла. Не нужно блокировать базу, нет сложных схем. Для личной базы знаний — идеально. *(Заменён на SQLite в v1.11.)*

### Версия 1.1 — Документы и чанкинг
Добавлена работа с файлами и большими документами:
- `mem add-file file.txt` — сохранить файл
- `mem index ./папка/` — проиндексировать папку
- **Чанкинг**: большие документы автоматически разбиваются на куски (чанки)
- Поддержка .txt, .md, .csv, .json, .pdf
- Source-команды: `mem source <id>` и `mem sources`

**PDF/DjVu/OCR:** импорт сначала использует встроенный текст (`pdftotext`/`mutool` для PDF, `djvutxt` для DjVu). Если текста нет или он слишком бедный, страницы последовательно рендерятся и распознаются локальным Tesseract. Инструменты ищутся в project config, `MEM_*` env, `PATH` и стандартных каталогах Windows; системный `PATH` не изменяется.

### Версия 1.2 — Заголовки записей
Раньше записи были безымянными. Теперь у каждой записи может быть заголовок:
- `mem add "текст" -title "Название"`
- В результатах поиска заголовок показывается первой строкой
- В `mem recent` заголовок вместо обрезанного текста
- Если заголовка нет — пишет «(без заголовка)»

### Версия 1.3 — Версия и авторские права
Добавлено отображение версии:
- `mem version` — краткая информация
- `mem` без параметров — версия + справка
- Копирайт: «(c) 2026 Кнап Руслан Юрьевич»

### Версия 1.4 — Фильтр по тегам при поиске
Теги работали только при добавлении, теперь и при поиске:
- `mem search "сервер" -tags "инфраструктура"`
- Фильтр AND-подобный: показываются записи, содержащие хотя бы один из указанных тегов
- Сравнение регистронезависимое

### Версия 1.5 — Фильтр по дате
Поиск во временном диапазоне:
- `mem search "сервер" -from 2026-06-01 -to 2026-07-01`
- Формат даты: YYYY-MM-DD
- Дата создания хранится в RFC3339, при фильтрации парсится

### Версия 1.6 — Порог релевантности (min-score)
Отсев нерелевантных результатов:
- `mem search "сервер" -min-score 0.5`
- По умолчанию 0.0 (не фильтровать)
- Применяется ПОСЛЕ всех бустов (гибрид + реранжирование)

### Этап надёжного поиска и цитирования
По умолчанию `mem search` строит полный отфильтрованный candidate set до
окончательного `-limit`: фильтры не применяются к уже обрезанному vector top-K,
а точное lexical-свидетельство не теряется за нерелевантными векторами.

Локальный lexical-слой использует SQLite FTS5/BM25 (в текущем pure-Go build
FTS5 доступен). Если конкретная сборка SQLite не предоставляет FTS5, поиск
детерминированно переходит на token-based fallback; это fallback, а не оценка
вероятности релевантности. FTS перестраивается лениво после открытия базы или
изменения записей, одной SQLite-транзакцией; повторный read-only поиск не делает
полный rebuild. `-vector-only` отключает lexical-кандидатов.

Итоговый fusion score прозрачен: `0.5 * vector_score + 0.5 * lexical_score`,
где обе компоненты нормализованы в диапазон 0..1. Если lexical совпадений нет,
сохраняется vector score. После fusion остаётся совместимый re-ranking по
свежести/тегам/важности, затем `-min-score` и только потом `-limit`.

Каждый результат содержит строку `[CITE]` с детерминированным source anchor и
отдельным читаемым label. Для новых provenance-aware chunks anchor строится из
идентификатора документа, физической page, исходного block и номера чанка внутри
этого блока. Поэтому изменение числа чанков в более раннем блоке не переименовывает
якоря следующих блоков. Label включает source, page, block и глобальный chunk;
legacy rows без новых block-local координат используют совместимый fallback, не
получают выдуманную страницу и помечаются `(no provenance)` при полном отсутствии
provenance. Source anchor намеренно не содержит ревизию: он обозначает логическое
место в документе. Отдельные `document_revision` и `chunk_hash` показывают, из
какой версии документа и какого точного текста получено evidence.

### Grounded answers: `mem ask`

`mem search` остаётся сырым поиском и не вызывает генеративную модель. Для
локального ответа только по найденным фрагментам используется отдельная команда:

```powershell
mem ask "На какой странице описан запуск сервера?" -limit 5
mem ask "что сказано о резервном копировании" -tags "инфраструктура" -context-chars 8000
```

Стадии retrieval/evidence/generation выводятся в `stderr`, а проверенный ответ и
источники — в `stdout`. Evidence сериализуется как недоверенные данные, содержит
source anchor, `document_revision`, хеш полного чанка и отдельный хеш точного
текста prompt. Если текст пришлось обрезать по бюджету, это явно отмечается как
`truncated`, поэтому хеш полного чанка не выдаётся за хеш отправленного фрагмента.

Контракт с моделью fail-closed: она должна вернуть ровно один JSON object либо с
`claims`, где у каждого тезиса есть непустой список точных коротких ссылок
`E1`, `E2`, ... из `evidence_ref`, либо с `insufficient_evidence`. Приложение
само преобразует эти ссылки в полные SHA-256 citation ID. Свободный текст, лишние
поля и неизвестные ссылки отклоняются до вывода. Проверка гарантирует, что каждый
выведенный тезис ссылается на реально переданный evidence, но не доказывает
семантическую истинность тезиса — интерпретацию локальной модели всё равно нужно
оценивать критически.

Для локальных моделей запрос использует `think:false` и `format:"json"`.
Для YandexGPT в 1.32.0 вместо строкового `format` передаётся строгая JSON Schema,
где enum citations построен только из evidence текущего запроса. Уже совместимые
модели сохраняют прежний формат. Точная оболочка `{"answer":"..."}` у прочих
локальных моделей получает один schema-retry; более широкого автоматического
исправления нет, чтобы не принять неподтверждённый ответ.
`done_reason: length` сообщается как исчерпание `answer.max_tokens`, а скрытое
`message.thinking` никогда не принимается за финальный ответ.

Для `ask` требуется отдельная локальная chat/instruct-модель Ollama. `bge-m3`
остаётся только embedding-моделью и не выбирается автоматически. Answer endpoint
принимает только `localhost`, `127.0.0.1` или `::1`; HTTP redirects не следуются.
Однако модель с тегом `:cloud` Ollama самостоятельно выполняет в Ollama Cloud,
поэтому для полностью локальной обработки выбирайте модель без cloud-тега.

### Расширенная карта знаний: фундамент graph-модели

После стабилизации provenance добавлен persistence-контракт именно для графа,
а не для примитивного дерева. Backend-фундамент и ограниченное локальное
LLM-извлечение доступны через CLI; автономный HTML остаётся read-only, а live
loopback-пространство поддерживает защищённые review-решения, правки и undo.

Поддерживаемые типы узлов разделены на три слоя:

- источник: `document`, `section`, `topic`, `definition`, `claim`, `formula`,
  `example`, `procedure`, `event`;
- аналитика: `comparison`, `contradiction`, `gap`, `dependency`, `cause`,
  `effect`, `risk`, `constraint`;
- рабочие объекты: `note`, `question`, `card`, `hypothesis`, `decision`, `task`.

Связи также типизированы: `contains`, `about`, `supports`, `contradicts`,
`derived_from`, `asks`, `answers`, `prerequisite`, `related`, `compares`,
`reveals_gap`, `resolves`, `defines`, `exemplifies`, `depends_on`, `causes`,
`mitigates`, `constrains`, `precedes`, `happens_before`, `hypothesizes_about`, `based_on`,
`acts_on`. Узел может иметь несколько входящих и
исходящих связей, поэтому модель поддерживает сравнение документов,
перекрёстные темы, последовательности, зависимости и причинно-следственные
цепочки без сведения структуры к иерархии.

Каждый узел и каждая связь обязаны иметь хотя бы один `EvidenceAnchor`. Anchor
содержит стабильный citation ID, document/chunk revision, source coordinates,
точную выдержку и её SHA-256. Ручные и generated-узлы не освобождаются от этого
правила. При повторном импорте состояние anchor определяется как:

- `current` — location, document revision, chunk hash и выдержка совпадают;
- `stale` — логический source anchor ещё существует, но ревизия/evidence изменились;
- `missing` — source anchor больше не найден.

`UpsertKnowledgeGraph` атомарно обновляет переданный фрагмент графа и его evidence,
не стирая другие ветви. SQLite хранит узлы, связи и evidence в отдельных таблицах
`knowledge_nodes`, `knowledge_edges`, `knowledge_node_evidence` и
`knowledge_edge_evidence`.

Строгое извлечение запускается отдельно от поиска:

```powershell
mem map build "архитектура импорта" -limit 10
mem map build "сравнение требований двух документов" -tags "нормативы" -context-chars 16000
mem map analyze "требования к рабочему давлению" -context-chars 32000
mem map analyze "требования к рабочему давлению" -context-chars 32000 -batches 8
mem map analyze "требования к рабочему давлению" -context-chars 32000 -batches 8 -resume kar-0123456789abcdef0123456789abcdef
mem map duplicates --json -kind claim -threshold 0.92
mem map merge-node merge-node.json
mem map merges --json
mem map runs
mem map runs --json -status running
mem map run kar-0123456789abcdef0123456789abcdef --json
mem map prune-runs -older-than 30d -keep 20
mem map prune-runs -older-than 30d -keep 20 --yes
mem map status
mem map status --json
mem map approve node kn-0123456789abcdef0123456789abcdef --reviewer "Руслан" --comment "Проверено по документу"
mem map approve-batch review-manifest.json
mem map reviews --json -limit 100
mem map edits --json -limit 100
mem map export
mem map export-html knowledge-map.html --title "Карта проекта"
```

`map build` использует тот же hybrid retrieval и локальную chat/instruct-модель,
что и `mem ask`, но берёт только chunks с versioned document provenance. Модели
передаются недоверенный evidence JSON и точные citation ID. Она может предложить
только тип, текст, confidence, временный ref и связи между refs. Source path,
страница, block/chunk coordinates, document revision, hashes, постоянные node/edge
ID и полные `EvidenceAnchor` восстанавливает сам `mem` из доверенного retrieval-
контекста. Повтор одинакового извлечения получает те же IDs и не дублирует объекты.
Все generated-узлы и связи сохраняются со статусом `draft`: наличие допустимой
citation подтверждает происхождение, но не заменяет семантическую проверку.

`map analyze <фокус>` выполняет отдельный междокументный проход по уже
подтверждённым узлам `claim`. В prompt попадают только `active` claims, у которых
каждый anchor остаётся `current`; draft/resolved claims и active claims со
stale/missing evidence исключаются. До вызова модели должны поместиться минимум
два claims и минимум два разных `document_id`, иначе команда сообщает о
недостаточности данных и не вызывает модель.

По умолчанию `map analyze` сохраняет совместимое поведение с одним пакетом.
Флаг `-batches N` (от 1 до 32) включает детерминированное планирование нескольких
context-bounded пакетов. Планировщик сначала использует ещё не покрытые claims и
только при необходимости повторно добавляет уже покрытый claim как междокументный
мост. Каждый пакет имеет стабильный host-derived `batch_id`, содержит минимум два
claims и evidence минимум двух документов. Команда сообщает число eligible,
covered и uncovered claims; поэтому ограничение `-batches` не выдаётся за полный
анализ корпуса.

Внутри каждого пакета планировщик использует semantic affinity сохранённых
embeddings: для claim строится центроид только тогда, когда каждый его current
anchor разрешается в entry с одинаковым непустым `embedding_space` и размерностью.
`embedding_space` — SHA-256 fingerprint backend, точной настроенной модели и
нормализованного endpoint; API key и сам endpoint в строке БД не сохраняются.
Seed остаётся
focus-ranked и детерминированным, а партнёры из других документов выбираются по
максимальному cosine similarity. Claims без полного вектора и пары с несовместимыми
embedding-space/dim обрабатываются прежним стабильным fallback-порядком. В stderr и
финальной сводке отдельно показаны `semantic` и `fallback` batches.

Миграция SQLite добавляет `embedding_model` и `embedding_space` без переписывания
старых строк. Новые `mem add`, `add-file`, `index`, `import`, переэмбеддинг через
`edit`, поиск и Telegram-бот используют identity-aware пути. Старые записи остаются
доступны для чтения и лексического поиска, но их неизвестные векторы не сравниваются
с запросом из известного пространства и не участвуют в semantic clustering. Для
возврата таких записей в векторный поиск требуется повторная индексация/импорт или
переэмбеддинг.

Перед первым вызовом модели команда создаёт в SQLite детерминированный analysis
run `kar-...`: его ID зависит от фокуса, параметров генерации, точного prompt
каждого пакета и versioned evidence. Каждый строгий валидный batch-result сохраняется как
checkpoint с SHA-256 digest; raw-ответ модели в checkpoint не попадает. Повтор той
же команды автоматически пропускает `completed`/`insufficient` пакеты и повторяет
только `pending`/`failed`. Флаг `-resume <run-id>` дополнительно фиксирует ожидаемый
run: если claim, evidence, фокус или параметры изменились, возобновление
отклоняется до обращения к модели.

История checkpoints управляется отдельно от карты. `mem map runs` показывает
запуски от новых к старым, покрытие и число `pending/completed/insufficient/failed`
пакетов; `-status running|completed`, `-limit N` и `--json` позволяют отфильтровать
вывод. `mem map run <run-id>` загружает один запуск вместе с checkpoint-статусами,
причинами ошибок/недостаточности и сохранёнными проверенными фрагментами графа.

`mem map prune-runs -older-than 30d -keep 20` только показывает кандидатов.
Удаление выполняется лишь при явном повторе с `--yes`, одной транзакцией удаляя
run и его batches. Кандидатами бывают только `completed` старше cutoff, а последние
`-keep N` завершённых запусков защищены независимо от возраста. `running` никогда
не удаляются этой командой: в том числе запуск с `failed` batch остаётся доступным
для повторного `map analyze`/`-resume`. Для автоматизации доступны `--dry-run` и
`--json`; `--dry-run` и `--yes` взаимоисключающие.

Семантические дубликаты также обрабатываются отдельным review-gated workflow.
`mem map duplicates` эмбеддит точный текст `label + body` каждого выбранного узла
в текущем configured `embedding_space` и сравнивает только узлы одинакового kind.
Документные chunk-векторы для этого не переиспользуются: два разных утверждения
из одного chunk иначе получили бы ложное сходство. Узлы с `stale/missing` evidence
и уже `resolved` исключаются. По умолчанию threshold равен `0.92`, `-nodes 200`
ограничивает число вызовов embedding API, а `-limit 100` — число показанных пар.
Команда только строит кандидатов и не меняет карту автоматически.

Когда пара состоит из generated `draft` и `active` узла того же kind, отчёт
предлагает первый как `source`, второй как канонический `target`. Для объединения
нужен явный JSON-манифест и ручно заявленный reviewer:

```json
{
  "source_id": "kn-source",
  "target_id": "kn-canonical",
  "reviewer": "Руслан",
  "comment": "Один и тот же норматив",
  "expected_source_node_digest": "sha256:...",
  "expected_target_node_digest": "sha256:...",
  "expected_source_evidence_digest": "sha256:...",
  "expected_target_evidence_digest": "sha256:...",
  "similarity": 0.97,
  "embedding_space": "sha256:..."
}
```

`mem map merge-node merge-node.json` повторно проверяет оба node/evidence digest,
current-состояние всех anchors, одинаковый kind и статусы `generated draft ->
active`. Это логическое, недеструктивное объединение: source и его provenance не
удаляются, а получают `resolved`; его generated draft-связи также становятся
`resolved`. Active или manual/source-связи блокируют операцию вместо скрытой потери
семантики. Решение записывается одновременно в `knowledge_reviews` (`action=merge`)
и append-only `knowledge_node_merges`.

Повторное извлечение с тем же точным содержимым и evidence сохраняет объединение.
Изменение source/target content digest, evidence digest или статуса target делает
запись stale и при следующем graph-upsert возвращает generated source и его связи
в `draft`. `mem map merges [--json]` показывает полную историю и флаг `current`;
старые записи не переписываются. Значение similarity является зафиксированным
результатом детектора, а не доказательством эквивалентности: окончательное решение
остаётся за reviewer.

Все проверенные ответы объединяются по постоянным host-derived IDs. Findings и
relations записываются в knowledge graph только после успешного завершения и
слияния всех пакетов; batch-checkpoints не являются частичной публикацией графа.
Ошибка generation/validation/merge не оставляет findings из уже обработанных
пакетов, но позволяет продолжить run без повторной оплаты завершённых вызовов.
`insufficient_evidence` одного пакета не мешает сохранить допустимые findings
других пакетов.

Модель может вернуть только findings типов `contradiction` и `gap`, ссылки вида
`c1`/`c2` и точные citation ID. Для contradiction требуются ровно два claims; для
gap — от двух до восьми. Каждый finding обязан цитировать evidence каждого
указанного claim и охватывать минимум два документа. Постоянные IDs, endpoints и
связи восстанавливает хост: contradiction получает прямую связь `contradicts` и
две `derived_from`, gap связывается с исходными claims через `reveals_gap`.
Findings и все их отношения сохраняются только как `draft`.

Перед транзакцией `map build` и `map analyze` повторно проверяют evidence под той
же write-lock, что используется для записи графа. Если документ изменился за
время локальной генерации, весь результат отклоняется без частичной записи.

`map status` строит review-отчёт по всем узлам и связям:
`draft/active/rejected/resolved`,
агрегированное состояние evidence, детерминированный `evidence_digest` и каждый отдельный anchor с состоянием
`current/stale/missing`. В обычном режиме это читаемый список; `--json` даёт
стабильный машинно-читаемый объект с summary и items. Draft считается готовым к
подтверждению только при полностью current evidence. Для связи дополнительно оба
endpoint-узла должны быть `active`.

`map approve <node|edge> <id> --reviewer <имя>` выполняет единственный review-переход
`draft -> active`. Автор обязателен, комментарий задаётся через `--comment`, а
`--evidence-digest` позволяет закрепить точный набор просмотренных anchors.
Проверка evidence, изменение статуса и добавление audit-записи выполняются атомарно;
`stale`, `missing`, уже active/rejected/resolved объект или draft-связь с неактивным
endpoint оставляют базу без изменений. Повторное generated-извлечение с теми же
точными anchors сохраняет подтверждённый статус. Если изменились revision, hash,
excerpt или набор anchors, объект снова становится `draft` и требует проверки.
Если при этом generated-узел перестал быть active, его ранее active generated-связи
также транзакционно возвращаются в `draft`.

В `mem map open` тот же объект можно отклонить переходом `draft -> rejected`;
для этого обязательна причина. `rejected -> draft` выполняется отдельным действием
«ВЕРНУТЬ В РАБОТУ», поэтому журнал различает новое решение и отмену старого.
Статус `resolved` зарезервирован для объектов, закрытых другими операциями, и не
используется как синоним отказа.

Undo доступен только для последней обратимой review-записи (`approve`, `reject`
или `reopen`) при точном совпадении номера записи, текущего статуса и
`evidence_digest`. Историческая строка не удаляется: добавляется новая запись
`action=undo` с `reverts_review_id`. Отмена подтверждения endpoint-узла блокируется,
пока остаётся хотя бы одна активная связь. Это требует сначала отменить решения
по связям и не допускает активных отношений с неподтверждёнными концами.

Для пакетной проверки используется явный манифест, а не команда «подтвердить всё»:

```json
{
  "reviewer": "Руслан",
  "comment": "Проверено по первичным источникам",
  "objects": [
    {
      "object_type": "node",
      "id": "kn-0123456789abcdef0123456789abcdef",
      "expected_evidence_digest": "sha256:..."
    }
  ]
}
```

`mem map approve-batch review-manifest.json` строго отклоняет неизвестные поля,
дубликаты, пустой пакет и объекты без digest. Узлы и их связи можно включить в
один манифест в любом порядке. Все статусы и audit-записи фиксируются одной
SQLite-транзакцией; несовпадение хотя бы одного digest, stale/missing evidence или
неактивный endpoint откатывает пакет целиком. `mem map reviews [--json] [-limit N]`
показывает append-only историю решений, которая не стирается при повторном
извлечении или смене evidence.

`mem map edits [--json] [-limit N]` отдельно показывает append-only историю
названий и описаний. Review-решения и содержательные правки намеренно не смешаны:
у них разные причины, поля и правила undo.

Поле `reviewer` сейчас является локально заявленной строкой, а audit-журнал —
локальной метаинформацией SQLite, не криптографической подписью и не проверенной
учётной записью. Защита от UPDATE/DELETE реализована в схеме БД, но владелец файла
базы всё равно может удалить или заменить сам файл.

Ответ модели обязан быть одним строгим JSON object: `nodes`/`edges` либо
`insufficient_evidence`. Лишние поля, неизвестная citation, связь с неизвестным
ref, пропущенный confidence/evidence, неподдерживаемый тип и превышение лимитов
100 nodes / 300 edges отклоняют весь результат до транзакции. При честном
`insufficient_evidence` или отсутствии versioned chunks модель либо не вызывается,
либо база остаётся без изменений. `map export` пишет полный сохранённый граф в JSON
на `stdout`.

`mem map export-html knowledge-map.html` создаёт интерактивный provenance-first
снимок всей карты, а не иерархическое дерево. HTML полностью автономен: CSS,
force-layout и данные встроены в один файл, внешних CDN, сетевых запросов и
серверного процесса нет. Существующий файл не перезаписывается без `--force`;
`--title` задаёт заголовок вкладки.

Визуализация поддерживает:

- направленные типизированные связи и несколько входящих/исходящих ветвей;
- force-layout, pan, zoom, fit и ручное перетаскивание узлов;
- восстановление сохранённой раскладки; в live-режиме drag закрепляет узел,
  двойной щелчок освобождает его, а pan/zoom/FIT автоматически сохраняются;
- детерминированные тематические кластеры по ближайшей теме/документу, цветовая
  cluster-layout раскладка и быстрый фокус на одном кластере;
- окружение выбранного узла глубины 1–3, сворачивание структурных ветвей и
  возврат полной карты без изменения самого графа;
- именованные visual views с сохранением координат, viewport, фильтров,
  cluster-layout, focus/collapse и восстановлением последнего выбора браузера;
- перетаскиваемые границы левой и правой панели с сохранением ширины в браузере;
- тёмную и светлую темы с сохранением выбора и полным перекрашиванием карты;
- открытие текущего PDF-evidence на указанной физической странице из live-карты;
- редактирование названия и описания в live-карте с автором, комментарием,
  историей и безопасной отменой последней правки;
- поиск по ID, label, body и kind;
- независимые фильтры node kind, relation kind, `draft/active/rejected/resolved` и
  `current/stale/missing` evidence;
- особую геометрию/цвет для source-, analytics- и workspace-типов, а также
  подсветку критических `contradicts`/`reveals_gap`;
- создание ручных заметок, вопросов, карточек, гипотез, решений и задач из
  выбранного source-backed узла с типизированной связью и append-only аудитом;
- экспорт закреплённой выбранной области в JSON-ветвь, CSV-таблицу,
  Markdown-отчёт, план или checklist с координатами источников;
- детальную панель узла или связи с body, extraction confidence, evidence
  coverage, freshness, reviewer state, merge-target,
  evidence digest, точной выдержкой, source path, page, block/chunk coordinates,
  citation ID, document revision, chunk hash и evidence hash;
- адаптивные панели для узкого окна и клавиши `/` (поиск), `Esc` (сброс).

Автономный HTML является read-only snapshot: approval, редактирование, merge и
повторный анализ выполняются в live-карте или через проверяемые CLI-команды, после
чего файл нужно экспортировать заново. В него
попадают текущая сохранённая раскладка, evidence excerpts и локальные source paths,
поэтому такой файл
следует считать потенциально чувствительным и передавать только осознанно.

Эта проверка доказывает структурную привязку каждого объекта к реально переданному
evidence, но не доказывает семантическое следование утверждения из цитаты.
`map analyze` остаётся focus-driven анализом, а не доказательством отсутствия иных
противоречий во всём корпусе. `-batches` сообщает покрытие claims, но не означает
проверку всех попарных сочетаний: планировщик пока ранжирует по пересечению токенов
с фокусом, semantic affinity и разнообразию документов. Текущая кластеризация
greedy и не перебирает все попарные сочетания. Сохранённая identity подтверждает
настроенные backend/model/endpoint, но не является digest весов модели: текущие
embedding API не возвращают такой digest. Отдельная база `.fileindex` теперь
сохраняет ту же configured identity и допускает semantic search только внутри
точно совпадающего `embedding_space`; legacy-векторы без identity исключаются до
обычного `mem-index scan`. Автоматического объединения без review и совместного
многопользовательского редактирования пока нет. Live-карта читает актуальную базу
после обновления страницы; автономный HTML сам не синхронизируется.

### Версия 1.10 — Локальный режим (per-project базы)

**Проблема:** до v1.10 база жила в глобальной `~/.mem/store.jsonl`. Если запустить две копии `mem` параллельно в разных проектах — они работали с одной и той же базой, записи из разных проектов смешивались. *(В v1.11 формат сменился на SQLite — `store.db`.)*

**Решение:** каждая директория = своя изолированная база `./.mem/`. Хранится прямо в текущей папке, без подъёма вверх по дереву. Несколько копий `mem` в разных папках работают параллельно и не мешают друг другу.

**Структура `.mem/`:**
```
.mem/
├── config.json    # настройки (backend, model, chunking, api_key) — per-project
├── store.db       # записи (SQLite, эмбеддинги в BLOB) — *(до v1.11 был store.jsonl)*
└── meta.json      # метаданные базы (имя, дата создания)
```

**Команда `mem init`:** создаёт `.mem/` в текущей папке. Если `.mem/` уже есть — ошибка. Также база создаётся **автоматически** при первом `mem add`/`add-file`/`index`/`config`, если её нет.

**Настройки эмбеддингов тоже per-project:** `mem config set-backend polza` в одной папке не влияет на другую. Каждый проект настраивает свою базу независимо.

**Откат v1.10.0 (именованные базы):** была попытка сделать `mem db create/use/list` с глобальными именованными базами в `~/.mem/databases/` — откачена коммитом `2747afe`. Оказалась неудобной для параллельной работы. Локальный режим — проще и понятнее: cwd сам определяет, с какой базой работать.

**Команды без базы:** `mem version`, `mem help` — работают всегда. Остальные требуют `.mem/` в cwd (с автосозданием или без).

### Версия 1.14 — Интерактивный REPL

**Проблема:** если работать в каталоге проекта и часто искать в базе, голый CLI `mem search ...` утомляет: каждый раз вводить `mem` и подкоманду. Хочется REPL как в `psql`, `sqlite3` или Claude Code — prompt внизу, история, автодополнение.

**Решение:** режим `mem repl` (явный запуск). Открывается prompt `mem>`, можно вводить запросы и `/`-команды, история сохраняется в `.mem/history.txt` (per-project). С версии 1.15 `mem` без аргументов по умолчанию запускает TUI (см. ниже), а REPL доступен через `mem repl`.

**Стартовый экран:**
```
mem · поисковая база · 35 записей · backend: ollama · bge-m3

Последние записи:
[*] #63  v1.13.0: цветной вывод mem CLI (фаза 1 UX)
[*] #62  UX-дизайн: цвета, подсветка, таблицы
...
──────────────────────────────────────────────────
mem> _
```

**Команды REPL:**

| Ввод | Что делает |
|---|---|
| `<текст>` | Сокращение для `/search <текст>` |
| `/search <q>` | Поиск |
| `/add <текст>` | Добавить запись |
| `/recent` | Последние N |
| `/show <id>` | Показать запись |
| `/important <id>` | Переключить важность |
| `/tags <id> -tags ...` | Изменить теги |
| `/edit <id> <текст>` | Изменить запись |
| `/delete <id>` | Удалить |
| `/stats` | Статистика |
| `/sources` | Список документов |
| `/config` | Конфигурация |
| `/clear` | Очистить экран |
| `/clear-history` | Очистить историю ввода |
| `/help` | Справка по `/`-командам |

**v1.15.5 — TUI больше не падает на ошибках в хендлерах:**
- **Баг:** `/edit 2` (без нового текста) или любая другая команда с невалидными аргументами убивали TUI через `os.Exit(1)` из хендлера. В терминале печаталось «Ошибка: ...», но TUI-процесс полностью вываливался.
- **Причина:** все хендлеры (`handleEdit`, `handleShow`, `handleDelete`, `handleRetag`, `handleImportant`, `handleAdd`, `handleSearch`, `handleRecent`, `handleStats`, `handleSources`) писали ошибки в `os.Stderr` + вызывали `os.Exit(1)`. Для CLI это нормально, но из TUI-горутины `os.Exit` убивает весь процесс. Плюс `captureStdout` ловит только `os.Stdout`, а `os.Stderr` шёл в реальный терминал — ошибки не попадали в viewport.
- **Фикс (системный):**
  - Сигнатуры 11 хендлеров изменены: возвращают `error` вместо `void`. `os.Stderr + os.Exit(1)` заменены на `return fmt.Errorf(...)`. Префикс «Ошибка: » в сообщениях убран — его добавляют диспатчеры.
  - CLI-диспатч в `main()`: `if err := handler(...); err != nil { fmt.Fprintf(os.Stderr, "Ошибка: %v\n", err); os.Exit(1) }` — поведение CLI сохранено.
  - REPL-диспатч в `dispatchReplLine()`: то же, но без `os.Exit` — REPL продолжает работать после ошибки.
  - TUI-горутина в `runCommandAsync()`: ошибка пробрасывается в `execResultMsg.err` и отрисовывается в viewport через `"Ошибка: " + err.Error()` — TUI остаётся живым и принимает следующие команды.
  - В TUI добавлен локальный хелпер `runWithCapture(fn func() error)` — запускает хендлер с перехватом stdout и пробрасывает ошибку в общий `err`, чтобы убрать копипасту в каждом case.
- CLI-only хендлеры `handleInit`/`handleSource` остаются отдельными путями; файловые команды возвращают ошибки диспетчеру, чтобы partial failure не маскировался под успех.

**v1.15.8 — код-ревью: критичные баги (data integrity, resource safety):**
- Проведено код-ревью TUI-стека (bubbletea/bubbles/lipgloss) и backend (SQLite/readline) с подключением **context7 MCP** для сверки с актуальной документацией. Всего 19 находок. v1.15.8 закрывает 4 критичных.
- **Фикс 1: `captureStdout` panic-safe.**
  - **Было:** `os.Pipe()` + горутина с `io.Copy` + `fn()` без `defer Close`. Если `fn()` паникует — `w.Close()` не вызывается → `io.Copy` блокируется до EOF на read-end → утечка pipe-FD и горутины.
  - **Стало:** `defer func() { _ = w.Close(); os.Stdout = oldStdout }()` — pipe закрывается даже при panic. Panic продолжит распространяться к outer `recover` в `runCommandAsync`, и TUI увидит «Ошибка: паника в обработчике: ...» вместо зависания.
- **Фикс 2: `Store.Close()` + `defer` во всех путях.**
  - **Было:** `Store` не имел метода `Close()` — SQLite-соединение никогда не закрывалось явно (только при выходе процесса). На Linux/Mac это OK, на Windows приводит к ошибкам «database is locked» при следующем запуске.
  - **Стало:** добавлен `func (s *Store) Close() error { return s.db.Close() }`. В `cmd/mem/main.go` функция `main()` разделена на `main() → run() int`, в `run()` сразу после `newStore` стоит `defer store.Close()`. Это работает для всех веток: CLI-команды, `runRepl`, `runTui`.
- **Фикс 3: `GetByID`/`GetBySourceFile`/`ToggleImportant` возвращают копии.**
  - **Было:** `GetByID` возвращал `*Entry` на внутренний слайс после `RUnlock`, `GetBySourceFile` — `[]*Entry` на те же внутренние структуры. Внешний код мог читать/менять состояние `Store` конкурентно после снятия лока → race condition / data corruption.
  - **Стало:** `GetByID` и `ToggleImportant` возвращают указатель на локальную копию `Entry` с глубокими копиями `Tags` и `Embedding` (`append([]string(nil), e.Tags...)`, `append([]float32(nil), e.Embedding...)`). `GetBySourceFile` возвращает `[]Entry` (не `[]*Entry`) — каждая запись это копия. Вызывающий код (`handleShow`, `handleImportant`, `showAllChunksFromFile`) уже совместим.
- **Фикс 4: `Add`/`AddChunk`/`UpdateById` копируют `tags` и `embedding`.**
  - **Было:** `entry.Tags = tags` / `entry.Embedding = embedding` сохраняло caller-слайсы прямо в кэш `Store`. Если caller мутирует свой слайс после вызова — кэш меняется без блокировки → рассинхрон с БД.
  - **Стало:** перед сохранением делается копия `tagsCopy := append([]string(nil), tags...)`, `embCopy := append([]float32(nil), embedding...)`. В кэш попадает копия, БД сериализуется из копии, caller-слайс остаётся независимым.

**v1.15.9 — код-ревью: качество TUI (best practices, performance):**
- Закрывает 5 средних находок из код-ревью (TUI-стек).
- **Фикс 5: spinner тикает только когда `m.busy=true`.**
  - **Было:** `Init() tea.Cmd { return tea.Batch(textarea.Blink, spinner.Tick) }` — deprecated package-level `spinner.Tick` тикал 10 FPS непрерывно, даже когда TUI простаивал (трата CPU).
  - **Стало:** `Init()` возвращает только `textarea.Blink`. Spin запускается в `Update` в ветке `enter` (когда пользователь сабмитит команду) через `tea.Batch(cmd, m.spinner.Tick)`. Sync-команды (`/clear`, `/help`, `/exit`) по-прежнему не трогают спиннер.
- **Фикс 6: bounded buffer для `m.output`.**
  - **Было:** `m.output []string` рос неограниченно при длинных сессиях — каждая команда добавляла блок, и `strings.Join(m.output, "\n")` в `View` становился O(n²).
  - **Стало:** добавлена константа `maxOutputLines = 500`. В `appendBlock` после append: если `len(m.output) > maxOutputLines` — отбрасываем самые старые блоки. Память ограничена, `View` остаётся быстрым.
- **Фикс 7: `View()` через `lipgloss.JoinVertical`.**
  - **Было:** `return fmt.Sprintf("%s\n%s\n%s%s\n%s\n%s\n%s", header, sep, viewportView, popupView, sep, taView, status)` — `fmt.Sprintf` со склейкой через `\n` мог сломать layout, если элемент сам содержит переводы строк.
  - **Стало:** `lipgloss.JoinVertical(lipgloss.Top, header, sep, viewportView+popupView, sep, taView, status)` — стандартный lipgloss-способ склеить вертикальный layout. Корректно обрабатывает встроенные `\n` в каждом элементе.
- **Фикс 8: cleanup alt-screen при panic в `runTui`.**
  - **Было:** `runTui` не имел защиты от panic — если `tea.Cmd` паниковал, TUI оставался в alt-screen mode, и терминал пользователя оставался «грязным» до `reset`.
  - **Стало:** в `runTui` добавлен `defer func() { recover() + ReleaseTerminal() }` — при panic явно вызывается `p.ReleaseTerminal()` для возврата терминала в нормальный режим, затем panic продолжает распространяться. В этой версии bubbletea нет метода `Program.Release()` (он появится позже), используется доступный `ReleaseTerminal()`.
- **Фикс 9: Enter не конфликтует с InsertNewline.**
  - **Было:** `ta.KeyMap.InsertNewline.SetEnabled(true)` — textarea реагировал на Enter как на newline, и тот же Enter сабмитил команду. Видно было вспышку `\n` в textarea перед сабмитом.
  - **Стало:** `ta.KeyMap.InsertNewline = key.NewBinding(key.WithKeys("ctrl+j"))` — InsertNewline перебинжен на `ctrl+j`. Enter — только сабмит. Ctrl+J — для вставки реального newline (если когда-нибудь понадобится для multiline prompt).

**v1.15.10 — код-ревью: качество backend (error handling, SQL):**
- Закрывает 4 средних находки из код-ревью backend (SQLite/readline).
- **Фикс 10: `LastInsertId`/`RowsAffected` проверяют ошибки.**
  - **Было:** `id, _ := res.LastInsertId()` и `n, _ := res.RowsAffected()` — ошибки проглатывались. Если драйвер не смог вернуть id — `id = 0`, дальше в коде получали запись #0 вместо ошибки.
  - **Стало:** `Add` и `AddChunk` возвращают `fmt.Errorf("получение LastInsertId: %w", lastErr)` при ошибке. `DeleteById` и `UpdateById` проверяют `rowsErr` от `RowsAffected()`. `UpdateById` дополнительно проверяет `n == 0` → возвращает «запись не найдена» (раньше молча возвращался nil).
- **Фикс 11: сериализация возвращает ошибки.**
  - **Было:** `floatsToBytes`, `bytesToFloats`, `tagsToJSON`, `tagsFromJSON` тихо проглатывали ошибки `binary.Read/Write` и `json.Marshal/Unmarshal`. Повреждённый BLOB в БД → `bytesToFloats` возвращал nil → запись «исчезала» из поиска без уведомления.
  - **Стало:** все 4 хелпера возвращают `(... , error)`. `bytesToFloats` дополнительно проверяет, что длина BLOB кратна 4 (размер `float32`), и возвращает явную ошибку про повреждение. `loadAll` оборачивает ошибку с ID записи: `fmt.Errorf("запись #%d: %w", e.ID, err)`. `Add`/`AddChunk`/`UpdateById` возвращают ошибки сериализации вызывающему коду.
- **Фикс 12: инициализация схемы в транзакции.**
  - **Было:** `db.Exec(storeSchema)` — SQLite выполняет DDL по одному выражению. При сбое между `CREATE TABLE` и `CREATE INDEX` база оставалась в полу-применённом состоянии (таблица без индексов).
  - **Стало:** добавлена функция `initSchema(db)` — оборачивает `tx.Begin() → tx.Exec(storeSchema) → tx.Commit()` с `Rollback` при ошибке. SQLite поддерживает transactional DDL.
- **Фикс 13: `Recent` сортирует по `created DESC`.**
  - **Было:** `Recent` возвращал хвост `s.entries` (отсортирован при `loadAll` по `id ASC`) и разворачивал — порядок определялся id, а не фактическим временем создания. Запись с большим id могла появиться «раньше» записи с меньшим id, если они были созданы в разных сессиях с расхождением часов.
  - **Стало:** `Recent` копирует `s.entries`, сортирует по `created DESC` (tie-breaker `id DESC`), возвращает первые `limit` записей. Сортировка в памяти (не SQL) — пользователь выбрал этот вариант.

**v1.15.11 — TUI UX: фикс спиннера, отмена через Esc, Ctrl+C×2 для выхода:**
- **Регрессия из v1.15.9:** после удаления `spinner.Tick` из `Init()` спиннер зависал на первом кадре — надпись «выполняю...» появлялась, но фреймы не менялись.
- **Фикс спиннера:** добавлен явный `case spinner.TickMsg` в `Update`. Теперь цепочка продолжается, пока `m.busy=true`; как только результат приходит — `busy=false`, и мы возвращаем `nil` вместо следующего tick. Спиннер не тикает впустую в idle.
- **Esc → отмена при `m.busy=true`:** новое поведение «как в Claude Code».
  - Если выполняется команда — Esc ставит `m.cancelled=true`, в viewport: «Отменяю... (дождитесь завершения операции)». TUI остаётся живым.
  - Когда горутина вернёт `execResultMsg`, проверка `m.cancelled` отбрасывает её результат, показывает «Отменено пользователем» и сбрасывает `busy`.
  - **Ограничение:** сама горутина продолжает работать (хендлеры не принимают context) — просто её вывод игнорируется. Для типичных embedding-запросов (1-5 сек) это нормально.
  - Если `m.busy=false` — Esc работает по-старому: выход из TUI.
- **Ctrl+C → одинарный = предупреждение, двойной = выход:**

  - Второй Ctrl+C в течение 2 сек → `tea.Quit`.
  - Если 2 сек прошли — флаг сбрасывается через `ctrlCResetMsg`, и первое нажатие снова считается «первым» (нет блокировки выхода навсегда).
- **Ctrl+D** — без изменений (всегда выход, EOF-семантика).

**v1.15.12 — TUI: критический фикс deadlock в `captureStdout` (результат не появлялся в viewport):**
- **Регрессия из v1.15.11:** TUI показывал `"> команда"` и спиннер, но результат в viewport не появлялся — TUI зависал в `busy=true` навсегда. CLI в той же папке работал корректно.
- **Корневая причина — deadlock в `captureStdout` (`cmd/mem/tui.go`):**
  - В v1.15.11 я перенёс `w.Close()` в `defer`, считая что так утечки не будет даже при панике.
  - Но `defer` выполняется ПОСЛЕ вычисления возвращаемого значения → `return <-done` блокируется навечно, потому что горутина-ридер ещё не дописала в `done` (она ждёт EOF на `r`, а EOF ждёт `w.Close()` в defer, который не запустится).
  - Цикл: `<-done` → горутина → EOF → `w.Close()` → `<-done`.
  - Результат: `runCommandAsync` навсегда зависает в `captureStdout`. `execResultMsg` никогда не приходит в event loop → `m.busy` навсегда `true` → результат не появляется в viewport.
  - CLI работает потому что `handleSearch` и др. вызываются напрямую из `main.go`, минуя `captureStdout`.
- **Фикс `captureStdout`:** закрыть `w` явно ДО `return <-done`. После `fn()`:
  ```go
  _ = w.Close()
  os.Stdout = oldStdout
  return <-done
  ```
  Горутина-ридер увидит EOF на `r`, допишет в `buf`, закроет `r`, запишет в `done` (буферизованный канал, capacity=1). `<-done` сразу же вернёт значение.
  - `defer` остаётся как страховка от паники в `fn()` — он закрывает pipe и восстанавливает stdout в аварийном пути (хотя `recover` в `runCommandAsync` всё равно ловит панику и шлёт `execResultMsg{err}`).
  - В горутине-ридере добавлен `_ = r.Close()` после `io.Copy` — закрываем read-end, чтобы не утекал FD.
- **Дополнительный фикс: двойной `m.spinner.Update(msg)`:**
  - В v1.15.11 я добавил `case spinner.TickMsg` с локальным `spCmd`, **не убрав** безусловный outer-вызов `m.spinner.Update(msg)` в начале `Update`.
  - Это давало двойную обработку TickMsg: сначала outer (инкрементировал `m.tag` и возвращал tick), потом case делал второй Update, который видел `tag mismatch` (`msg.tag != m.tag`) и возвращал `nil` — цепочка обрывалась после 2 тиков.
  - **Фикс:** убран безусловный outer-вызов и `spCmd` из var-блока + из финального `tea.Batch`. Spinner обновляется только в `case spinner.TickMsg` — правильный bubbletea-паттерн.
- **Не трогали:** UX-фиксы v1.15.11 (Esc отменяет, Ctrl+C×2 для выхода) оставлены без изменений.

### Версия 1.16 — mem-index: семантический каталог файлов (новый бинарь)

**v1.16.0 — `mem-index.exe`: поиск файлов по смыслу (не по точному имени):**

- **Проблема:** существующий `mem add-file` индексирует **содержимое** файла (чанки + embedding
  каждого чанка) — это не помогает найти **сам файл** по примерному/смысловому запросу.
  «Где та книга про японскую кухню?» — не решается текущим `mem`.
- **Решение — отдельный бинарь `mem-index.exe`** с собственной БД `.fileindex/` (SQLite),
  где хранятся метаданные файлов (путь, имя, размер, mtime, hash, аннотация) и
  embedding строки `name + parent_dirs + annotation`. Поиск — косинусом по embedding,
  с гибридным boost по имени файла (как в `mem`).
- **Сценарий:** есть диск с книгами (`D:\Books\`) где `.fb2`, `.pdf`, `.epub`, `.djvu`
  перемешаны. После `mem-index init D:\Books && mem-index enrich D:\Books` можно искать:
  ```
  mem-index find "книга про японскую кухню"   # семантически по аннотации
  mem-index find "Азимов роботы"               # точно в аннотации
  ```
- **Команды:**
  - `mem-index init <dir>` — создать `.fileindex/` + первый scan.
  - `mem-index scan <dir> [-enrich] [-no-embed]` — инкрементальный rescan.
    Быстрый skip применяется только к активной записи с неизменными mtime/size и
    точно совпадающим `embedding_space` (backend + model + endpoint fingerprint).
    `-no-embed` сохраняет новые файлы как metadata-only; они появятся в
    семантическом поиске после обычного `scan`/`enrich` с embedding. Старый вектор
    сохраняется вместе с исходной identity только когда поисковый текст не менялся.
  - `mem-index enrich <dir>` — повторный scan с извлечением аннотаций.
  - `mem-index find "запрос"` — семантический поиск с гибридным boost.
  - `mem-index list [-limit N] [-include-stale]` — последние записи.
  - `mem-index show <id>` — одна запись целиком (путь, метаданные, аннотация).
  - `mem-index stats` — статистика (всего/активных/stale/по расширениям).
  - `mem-index rm <id>` — удалить запись из каталога (не с диска).
  - Поддерживаются глобальные флаги `--global`, `--dir <path>`, `--color`.
- **Stale-handling:** записи с удалёнными/перемещёнными файлами помечаются `stale=1`,
  не удаляются. `list` по умолчанию скрывает их, `list -include-stale` показывает
  с пометкой `[STALE]`. Если файл вернулся на диск — следующий scan автоматически
  снимает stale (через Upsert со `stale=0`), даже если mtime и размер не изменились.
  Если обход файловой системы был неполным, stale-reconciliation не выполняется,
  ошибки печатаются, а команда завершается с ненулевым кодом.
- **Аннотации по форматам:**
  | Формат | Метод                                                                                  |
  |--------|----------------------------------------------------------------------------------------|
  | `.txt`, `.md` | первые 64 KB текста                                                           |
  | `.fb2`         | нативный `encoding/xml` парсит `<annotation>` (точное описание книги)       |
  | `.pdf`         | `pdftotext -f 1 -l 2` (если установлен; иначе пустая аннотация + warning)  |
  | `.epub`        | `archive/zip` + `encoding/xml`: `<dc:description>` + `<dc:title>` + `<dc:creator>` |
  | `.djvu`, `.djv`| `djvused -e print-meta` (если установлен; метаданные title/author/year, без OCR) |
  | другое         | пустая аннотация (но запись в БД создаётся — путь/имя/размер)               |
- **Пути в БД — относительно scan-root.** Если перенести `D:\Books` на `E:\` — база
  продолжает работать; достаточно `mem-index scan .` после переноса (mtime файлов
  скорее всего изменится, вызовется re-embed).
- **Embedding:** переиспользует `mem.GetEmbedding(cfg, text)` (Ollama bge-m3 1024-dim
  или Polza text-embedding-3-small 1536-dim). Тот же config.json, что у `mem`.
  В БД сохраняются `embedding_model` и безопасный `embedding_space` fingerprint

### Версия 1.11 — SQLite и дедупликация

**Проблема:** к v1.10 база хранилась в JSONL-файле. На папке с 40 PDF по 30–200 страниц каждая это давало 19–120 МБ JSONL в одной строке-записи. Любое `delete` или `edit` вызывало полную перезапись файла в RAM и обратно, поиск тоже требовал держать все эмбеддинги в памяти. Плюс `mem index` одной и той же папки дважды — дублировал все чанки.

**Решение:** миграция на SQLite через pure-Go драйвер `modernc.org/sqlite` (без CGO, без внешних библиотек).

**Структура `.mem/` после миграции:**
```
.mem/
├── config.json    # настройки (backend, model, chunking, api_key) — per-project
├── store.db       # записи (SQLite, BLOB-эмбеддинги, индексы) ← новое
└── meta.json      # метаданные базы (имя, дата создания)
```

**Что даёт SQLite:**

1. **Скорость.** Чтение/запись отдельных записей без полной перезаписи файла. `delete` и `edit` работают мгновенно даже на базе из 10 000+ чанков.
2. **Дедупликация при индексации.** Уникальный индекс `(source_file, chunk_index) WHERE source_file != ''` гарантирует, что повторный `mem index` того же файла не дублирует чанки, а обновляет их (`ON CONFLICT ... DO UPDATE`).
3. **BLOB для эмбеддингов.** Вектор `[]float32` сериализуется через `binary.LittleEndian` в компактный BLOB (4 байта на измерение). Для 1024-мерного bge-m3 это 4 КБ на запись против ~15 КБ в JSON.
4. **Бинарь вырос на ~6 МБ** (pure-Go SQLite внутри), но это разовая плата за стабильность на больших базах.

**Пример дедупликации:**
```powershell
# Проиндексировали папку
mem index ./docs/
#  [FILE] report.pdf — 47 чанков
#  Всего: 1 файл, 47 чанков

# Изменили report.pdf, индексируем снова
mem index ./docs/
#  [FILE] report.pdf — 47 чанков
#  Всего: 1 файл, 47 чанков   ← НЕ 94! ON CONFLICT обновил существующие чанки
```

**Важно:** `ON CONFLICT ... DO UPDATE` работает **только для записей с `source_file != ''`** (чанки документов). Ручные `mem add` записи с пустым `source_file` остаются как есть — их не трогаем при переиндексации.

**Драйвер:** `modernc.org/sqlite` v1.54.0 — pure-Go реализация SQLite. Никаких CGO-зависимостей, кросс-компиляция работает.

**Что НЕ изменилось:**
- Публичный интерфейс `Store` (методы `Add`, `AddChunk`, `Search`, `Recent`, `GetByID`, `SourceFiles`, `Stats`, `DeleteById`, `UpdateById`, `ToggleImportant`)
- Кеш в памяти (`s.entries []Entry` + `s.vectors [][]float32`) — загружается при старте, обновляется инкрементально
- Поведение команд, флагов, гибридного поиска, реранжирования

## Архитектура

### Общая схема работы

```
Пользователь → CLI (main.go) → Хранилище (store.go)
                                  ↕
                              SQLite БД (store.db)
                                  ↕
                            Эмбеддинги (embed.go)
                                  ↕
                         Ollama / Polza AI API
```

### Хранилище (store.go)

**Формат:** SQLite (с v1.11). Один файл `.mem/store.db`, встроенная pure-Go реализация через `modernc.org/sqlite`.

**Схема таблицы `entries`:**
```sql
CREATE TABLE entries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL DEFAULT '',
    text TEXT NOT NULL,
    tags TEXT NOT NULL DEFAULT '[]',      -- JSON-массив строк
    created TEXT NOT NULL,                -- RFC3339
    backend TEXT NOT NULL,                -- "ollama" / "polza"
	 embedding_model TEXT NOT NULL DEFAULT '', -- точное имя модели из config
	 embedding_space TEXT NOT NULL DEFAULT '', -- SHA-256 backend/model/endpoint
    dims INTEGER NOT NULL,                -- размерность эмбеддинга
    embedding BLOB NOT NULL,              -- float32 LE, dims * 4 байт
    source_file TEXT NOT NULL DEFAULT '',
    chunk_label TEXT NOT NULL DEFAULT '',
    chunk_index INTEGER NOT NULL DEFAULT 0,
    total_chunks INTEGER NOT NULL DEFAULT 0,
    important INTEGER NOT NULL DEFAULT 0  -- 0/1
);

-- Уникальный индекс для дедупликации чанков
CREATE UNIQUE INDEX idx_source_chunk
    ON entries(source_file, chunk_index)
    WHERE source_file != '';

CREATE INDEX idx_backend ON entries(backend);
```

**Сериализация эмбеддинга:** `[]float32` → 4 байта на измерение через `binary.LittleEndian`. Для bge-m3 (1024 измерения) = 4096 байт. При чтении — обратная конвертация.

**Дедупликация:** в `AddChunk` используется `INSERT ... ON CONFLICT(source_file, chunk_index) WHERE source_file != '' DO UPDATE SET ...`. Это значит, что при повторной индексации того же файла чанки не дублируются — обновляются. Ручные `mem add` записи (с пустым `source_file`) под индекс не попадают.

**Кеш в памяти:** `s.entries []Entry` + `s.vectors [][]float32` — загружается при старте через `loadAll()`. На каждой мутации (Add/Update/Delete) обновляется синхронно с БД, поэтому `Search` остаётся O(n) по RAM без обращения к SQLite. Поиск — чистый Go, без SQL-запросов по эмбеддингам.

**Удаление и редактирование:** hard delete (`DELETE FROM entries WHERE id = ?`) и `UPDATE` по ID. Никаких tombstone-флагов, никаких полных перезаписей файла.

### Поиск (search)

1. **Векторный поиск:** запрос → эмбеддинг → косинусная близость со всеми записями → сортировка → топ-N
2. **Фильтры** (применяются к результатам векторного поиска):
   - По тегам (`-tags`)
   - По дате (`-from`, `-to`)
3. **Гибридный буст:** полнотекстовые бонусы к векторным оценкам
4. **Re-ranking:** свежесть → совпадение тегов → важность
5. **Min-score:** отсев по порогу
6. **Вывод**

### Эмбеддинги (embed.go)

Два бэкенда:
- **Ollama** (по умолчанию): `bge-m3`, размер вектора 1024, работает локально
- **Polza AI**: OpenAI-совместимый API, размер вектора 1536

Настройка: `mem config set-backend polza` + `mem config set-polza-key <key>`

### Чанкинг (chunk.go)

Большие документы разбиваются на фрагменты. Три стратегии:

| Стратегия | Как режет | Когда использовать |
|-----------|-----------|-------------------|
| `paragraph` (по умолчанию) | По абзацам (двойной перенос строки) | Документы с чёткой структурой |
| `sentence` | По предложениям | Исходный код, списки |
| `fixed` | Фиксированный размер с перекрытием | Когда структура не важна |

Настройка:
```
mem config set-chunk-size 800    # размер чанка в символах (100-2000)
mem config set-chunk-overlap 100 # перекрытие между чанками
mem config set-chunk-strategy sentence
```

Если абзац больше maxSize — он дробится на предложения внутри себя.

**Важно:** Если PDF-извлечение выдаёт текст без границ предложений (нет точек с заглавными буквами), `splitSentences` может не найти, где разорвать. В этом случае предложение режется **фиксированно** — по символам с разрывом по пробелам. Overlap также учитывается внутри `maxSize`, поэтому ни одна стратегия не создаёт чанк длиннее настроенного лимита.

Дополнительная защита в `embed.go`: текст длиннее 2000 рун отклоняется с ясной ошибкой и советом уменьшить `chunk_max_size`. HTTP-клиент embedding имеет общий timeout 5 минут, а переданный context может отменить запрос раньше. Тихого усечения больше нет: сохранённый текст всегда совпадает с текстом, для которого рассчитан вектор.


**Флаги:**
| Флаг | Описание |
|------|----------|
| `-limit N` | Количество результатов (по умолч. 10) |
| `-tags "тег1,тег2"` | Фильтр по тегам |
| `-from 2026-01-01` | Начало диапазона дат |
| `-to 2026-07-01` | Конец диапазона дат |
| `-min-score 0.5` | Порог релевантности (0.0–1.0) |
| `-vector-only` | Только векторный поиск, без lexical-кандидатов |

**Форматы результатов:**
```
[ ] #6 [49%] (без заголовка) (2026-07-25)
   Текст записи...
   [SCORE] vector=0.490 lexical=0.000 fusion=0.490 final=0.490
   [CITE] cite-a1b2c3d4-2-2 архитектура.txt | chunk 2/2
   [TAG] документация, архитектура

[~] #15 [74%] VDS конфигурация (2026-07-26)
   Сервер работает на Ubuntu 22.04, Go 1.22, SQLite
   [TAG] сервер, ubuntu

[*] #19 [100%] Боевой сервер (2026-07-26) [!]
   Важная запись: боевой сервер ...
   [TAG] сервер, инфраструктура, важно
```

**Маркеры релевантности:**
- `[*]` — >90% (высокая релевантность)
- `[~]` — >70% (средняя)
- `[ ]` — ≤70% (низкая)
- `[!]` — запись помечена как важная

### `mem import <путь>`

Staged-импорт документов с provenance для последующего цитирования результата поиска.

```powershell
mem import ./book.md -tags "книга,справочник"
mem import ./manual.pdf -title "Руководство"
mem import ./scan.djvu -tags "скан,справочник"
```

Поддерживаются:

- Markdown (`.md`, `.markdown`). Маркеры отдельной строкой `<!-- page: N -->` сохраняются в каноническом Markdown и записываются как точный номер страницы каждого поискового чанка.
- PDF (`.pdf`): сначала текстовый слой через `pdftotext`, затем `mutool`; при пустом/бедном слое — постраничный OCR.
- DjVu (`.djvu`, `.djv`): сначала `djvutxt`; при отсутствии embedded text — последовательный рендер `ddjvu` и OCR.

Оба extractor-а создают канонический Markdown того же вида:

```markdown
# Заголовок документа

<!-- page: 1 -->

Текст первой страницы...

<!-- page: 2 -->

Текст второй страницы...
```

Пустой текст не считается успехом. OCR выполняется по одной странице, временный raster удаляется перед переходом к следующей странице, а общий временный каталог очищается при успехе, ошибке и отмене. `Ctrl+C` также отменяет активный запрос embedding. До embedding проверяется provenance-контракт: identity/path документа, SHA-256 ревизия канонического извлечённого содержимого, непрерывные block indices, неотрицательные страницы, непустой текст, допустимый extraction method и конечная OCR confidence. Для каждого чанка вычисляется отдельный SHA-256 хеш точного текста, отправленного в embedding.

Все чанки повторного импорта валидируются как единый набор и заменяются одной SQLite-транзакцией вместе с манифестом физических страниц: смешанные document identity/revision/media type, неверный chunk hash, разные размерности embedding, разрывы block-local координат или ошибка записи оставляют прежнюю версию документа целой. Изменение файла сохраняет path-derived `document_id`, но меняет `document_revision`; неизменившийся текст чанка сохраняет `chunk_hash`. В базе также сохраняются физическая страница, метод extraction, средняя Tesseract confidence и предупреждения low-confidence. LLM-коррекция OCR не выполняется.

Явные пути и OCR-настройки задаются в `.mem/config.json` в секции `ingest`; эквивалентные env: `MEM_PDFTOTEXT`, `MEM_MUTOOL`, `MEM_PDFINFO`, `MEM_PDFTOPPM`, `MEM_PYTHON`, `MEM_DJVUTXT`, `MEM_DJVUSED`, `MEM_DDJVU`, `MEM_TESSERACT`, `MEM_TESSDATA_DIR`, `MEM_OCR_LANGS`. Все requested languages (например, `rus+eng`) должны находиться в одном tessdata-каталоге.

### `mem import-status`

Показать page-level манифест текущей ревизии одного документа или всей базы:

API; сохраняются только ограниченные по длине диагностические сообщения (в том
числе короткий фрагмент ошибки инструмента) и page-level метаданные.

## Конфигурация

**Файлы:**
- `./.mem/config.json` — настройки базы (per-project)
- `./.mem/store.db` — записи SQLite (per-project)
- `./.mem/meta.json` — метаданные (имя, дата создания)

Содержимое `config.json` (создаётся при `mem init` или автосоздании):

```json
{
  "backend": "ollama",
  "ollama": {
    "base_url": "http://localhost:11434",
    "model": "bge-m3"
  },
  "answer": {
    "base_url": "http://localhost:11434",
    "model": "",
    "timeout_seconds": 60,
    "max_tokens": 512,
    "context_chars": 12000,
    "temperature": 0.1
  },
  "polza": {
    "base_url": "https://polza.ai/api/v1",
    "api_key": "",
    "model": "openai/text-embedding-3-small"
  },
  "chunking": {
    "chunk_max_size": 1000,
    "chunk_overlap": 100,
    "chunk_strategy": "paragraph"
  }
}
```

Содержимое `meta.json`:
```json
{
  "name": "имя-проекта",
  "created_at": "2026-07-26T23:00:00Z"
}
```

### Параметры

| Параметр | По умолчанию | Описание |
|----------|-------------|----------|
| `backend` | `ollama` | Бэкенд эмбеддингов: `ollama` или `polza` |
| `ollama.base_url` | `http://localhost:11434` | URL Ollama API |
| `ollama.model` | `bge-m3` | Модель эмбеддингов Ollama |
| `answer.base_url` | `http://localhost:11434` | Только loopback URL локального Ollama chat API; redirects запрещены |
| `answer.model` | (пусто) | Отдельная chat/instruct-модель для `mem ask`; `bge-m3` запрещена |
| `answer.timeout_seconds` | `60` | Общий deadline retrieval и generation |
| `answer.max_tokens` | `512` | Верхняя граница ответа |
| `answer.context_chars` | `12000` | Бюджет system + question + serialized evidence |
| `answer.temperature` | `0.1` | Параметр генерации Ollama |
| `polza.api_key` | (пусто) | API-ключ Polza AI (per-project!) |
| `polza.model` | `openai/text-embedding-3-small` | Модель Polza AI |
| `chunking.chunk_max_size` | 1000 | Макс. размер чанка в символах (100–2000) |
| `chunking.chunk_overlap` | 100 | Перекрытие между чанками (0–1000) |
| `chunking.chunk_strategy` | `paragraph` | Стратегия: `paragraph`, `sentence`, `fixed` |

**Важно:** настройки действуют только в текущей папке. В разных проектах — разные `config.json`, разные API-ключи, разные модели.

## Запуск Ollama

Для поиска нужен запущенный Ollama с моделью `bge-m3`:

```powershell
# В отдельном терминале:
ollama serve

# В другом терминале (один раз):
ollama pull bge-m3
```

Ollama должна быть доступна на `http://localhost:11434`.

Для `mem ask` установите отдельную локальную chat/instruct-модель и задайте её
в текущем проекте:

```powershell
mem config set-answer-model "<локальная-chat-модель>"
mem config set-answer-timeout 60
mem config set-answer-context-chars 12000
```

Без `answer.model` команда завершится явной ошибкой и не переключится на
embedding-модель. Удалённые answer URL отклоняются до отправки evidence.

```powershell
mem search "команды линукс" -from 2026-07-01
```

## Формат данных

Хранилище — `store.db` (SQLite) в директории `.mem/`. Один файл, одна таблица `entries`.

**Схема таблицы `entries`:**
| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | INTEGER PRIMARY KEY | Уникальный номер записи (AUTOINCREMENT) |
| `title` | TEXT | Заголовок (пустая строка, если не задан) |
| `text` | TEXT NOT NULL | Текст записи |
| `tags` | TEXT | JSON-массив тегов (по умолчанию `[]`) |
| `created` | TEXT NOT NULL | Дата в RFC3339 |
| `backend` | TEXT NOT NULL | Бэкенд эмбеддинга (`ollama` / `polza`) |
| `dims` | INTEGER NOT NULL | Размерность вектора |
| `embedding` | BLOB NOT NULL | Эмбеддинг: float32 LE, dims × 4 байта |
| `source_file` | TEXT | Исходный файл (пустая строка для ручных записей) |
| `chunk_label` | TEXT | Описание чанка (заголовок раздела) |
| `chunk_index` | INTEGER | Номер чанка в файле (0-based) |
| `total_chunks` | INTEGER | Всего чанков в файле |
| `document_id` | TEXT | Стабильная identity импортированного документа |
| `document_revision` | TEXT | SHA-256 ревизия канонического извлечённого содержимого |
| `chunk_hash` | TEXT | SHA-256 точного текста этого чанка |
| `source_path` | TEXT | Канонический абсолютный путь источника |
| `media_type` | TEXT | Тип источника (`text/markdown`, `application/pdf`) |
| `page` | INTEGER | Номер страницы, 0 если неизвестен |
| `block_index` | INTEGER | Номер исходного staged-блока (0-based) |
| `block_marker` | TEXT | Исходный маркер страницы/блока |
| `block_chunk_index` | INTEGER | Номер чанка внутри исходного блока (0-based) |
| `block_total_chunks` | INTEGER | Число чанков, полученных из исходного блока; 0 у старых строк |
| `extraction_method` | TEXT | `text` для embedded/Markdown или `ocr` для Tesseract |
| `ocr_confidence` | REAL | Средняя word-confidence Tesseract; `-1`, если OCR не применялся |
| `warnings` | TEXT | JSON-массив предупреждений extraction/OCR |
| `important` | INTEGER | Флаг важности: 0 или 1 |

**Индексы:**
- `idx_source_chunk UNIQUE (source_file, chunk_index) WHERE source_file != ''` — дедупликация чанков
- `idx_backend (backend)` — ускорение фильтрации по бэкенду

**Просмотр вручную:** установите [DB Browser for SQLite](https://sqlitebrowser.org/) и откройте `.mem/store.db` в текущей папке.

## Советы

1. **Используйте заголовки.** Запись с заголовком гораздо понятнее в результатах поиска.
2. **Тегируйте осмысленно.** Теги — основной способ фильтрации. Не бойтесь добавлять много тегов.
3. **Важное помечайте `-important`.** Пароли, ключи, критичные IP — сразу ставьте флаг.
4. **Крупные документы индексируйте через `mem index`.** Чанкинг разобьёт их на куски, каждый будет доступен для поиска отдельно. Повторный `mem index` того же файла **обновит** чанки через `ON CONFLICT`, не дублируя их.
5. **Не удаляйте бездумно.** `mem delete` стирает запись навсегда (hard delete в SQLite).
6. **Редактирование пересчитывает эмбеддинг.** Если вы просто меняете заголовок — эмбеддинг остаётся старым (текст не изменился).
7. **Резервируйте `store.db`.** Один файл с базой — просто скопируйте его в облако или Git (для приватных репозиториев). Для просмотра подойдёт [DB Browser for SQLite](https://sqlitebrowser.org/).
