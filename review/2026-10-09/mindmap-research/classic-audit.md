# Аудит классических карт мыслей mem-tool

Дата: 9 октября 2026 года. Рабочий материал для исследования возможностей и дальнейшего проектирования. Проверен текущий working tree, включая новые неотслеживаемые файлы; версия исходников — `1.71.0-alpha.37` (`internal/buildinfo/version.go:11`). Проверка статическая: прочитаны код, маршруты, браузерные обработчики и тесты. В этой исследовательской задаче тесты, сервер, сборка и модели не запускались. Наличие теста ниже означает наличие соответствующего сценария в репозитории, а не подтверждение его прохождения в данном исследовании.

Классические карты уже представляют собой самостоятельный редактор упорядоченного дерева с источниками, безопасной историей изменений, AI-предложениями, учебными карточками и восемью форматами экспорта. Основной пробел для изучения больших документов — качество общей структуры после пакетной генерации и продолжение учебной работы между посещениями. Это не отсутствующий с нуля модуль. Расширение следует проектировать поверх существующих контрактов ревизий, evidence anchors и атомарных изменений.

## 2. Модель данных и граница с knowledge graph

`pkg/mem/mind_map.go:21` прямо определяет классическую карту как отдельный от KnowledgeGraph слой. Каждый узел имеет одного родителя и позицию среди соседей. Это позволяет однозначно свернуть ветвь, экспортировать outline и отменить структурное изменение. Источник типа `knowledge_node` является ссылкой из дерева на объект графа знаний, а не дополнительным ребром между двумя узлами карты.

`ClassicMindMap` хранит название, описание, режим `manual/generated/hybrid`, статус `draft/ready/archived`, корень, ревизию и время изменений (`mind_map.go:34`, `:79`). Узел содержит `label`, `summary`, `body_markdown`, `kind`, `origin`, `locked`, JSON `style` и список источников (`:91`). Поддержаны девять типов: тема, подтема, факт, заметка, цитата, вопрос, задача, решение, ссылка (`:50`). Однако «задача» и «решение» — классификация содержимого: в структуре нет исполнителя, срока, состояния выполнения или отдельного журнала принятия решений.

Документ карты имеет формат версии 1, содержательный digest и resolved state digest (`:123`). Источники хранят citation ID, document ID/revision, chunk/evidence hash, путь, физическую страницу, номера блоков и сохранённый excerpt (`:108`, `:226`). Таблицы истории и снимков защищены от изменения уже записанных записей триггерами (`:324`). Поэтому новая возможность не должна обходить общий механизм мутаций прямым обновлением дерева из UI.

`style` присутствует в сохраняемой модели, но публичный node patch не предоставляет его редактирование (`:193`); интегрированная проекция WebMapNode не отдаёт ни style, ни origin (`pkg/mem/web_maps.go:39`). Нельзя считать произвольную настройку оформления узлов готовой только на основании колонки `style_json`.

## 3. Пользовательские поверхности и создание карты

Существуют три поверхности одной предметной области. CLI — `mem mindmap`; прежний локальный редактор — `mem mindmap open`; интегрированный редактор — раздел карт в `mem gui`/`mem serve`. Последние два имеют разные HTML/JavaScript и API. Проверка только одного редактора создаёт ложные выводы об отсутствии функций.

| Поверхность | Контракт и доказательства |
|---|---|
| CLI | Полный перечень `cmd/mem/mindmap.go:18`: create/list/show, add/edit/move/delete-node, source-add/remove/move, history/undo/redo, snapshot/snapshots, ai-new/expand/fill/sources/show/apply, templates/template-create, ask-branch/compare/study/export. |
| Локальный редактор | `pkg/mem/mind_map_live.go:22`, `:73`: отдельный loopback HTTP handler с capability-сессией. HTML — `pkg/mem/web/classicMindMapWorkspaceHTML.html`. API `/api/maps/*`, `/api/nodes/*`, `/api/sources/*`, `/api/history/*`, `/api/snapshots/*`, `/api/assistant/*`, `/api/workbench/*`. |
| Интегрированный редактор | `internal/webapp/maps.go:22`: `/api/v1/workspaces/{workspace}/maps`; AI-маршруты в `maps_ai.go:16`, вложения и ссылки на граф в `map_attachments.go:11`. Здесь действуют более строгие web-лимиты. |

Точные integrated API для реализации новых пользовательских сценариев ниже. Префикс `M` означает `/api/v1/workspaces/{workspace}/maps`, `{m}` — ID карты, `{n}` — ID узла. Все мутации — POST, кроме отдельно указанного чтения.

| Сценарий | Маршруты и точка dispatch |
|---|---|
| Создание/список/просмотр | `M`, GET `M`, GET `M/{m}`; шаблоны GET `M/templates`; `internal/webapp/maps.go:395`, `:399`, `:431`. |
| Текст и дерево | `M/{m}/nodes/{n}`, `.../children`, `.../move`, `.../delete`, `.../properties`; `maps.go:349`, `:367`. |
| Источники | GET `M/candidates`, GET `M/{m}/nodes/{n}/sources`, `.../source-add`, `.../source-remove`, `.../source-move`; `maps.go:172`, `:186`, `:204`. |
| Чтение оригинала | GET/HEAD `M/{m}/nodes/{n}/sources/{s}/document` и `/file`; `maps.go:135`. |
| AI | `M/from-sources`, `M/{m}/nodes/{n}/ai`; GET `M/{m}/ai`, GET `M/{m}/ai/{task}`, POST `.../{task}/cancel` и `/apply`; `maps.go:22`, `maps_ai.go:16`. |
| Ветка/учёба/вопрос | POST `M/{m}/nodes/{n}/branch` с ревизией возвращает данные ветви и study pack; POST `.../ask`; `maps.go:104`. |
| История | GET `M/{m}/history`, POST `/undo`, `/redo`, GET/POST `/snapshots`; `maps.go:265`, `:300`, `:314`. |
| Библиотека/обмен | `M/{m}/metadata`, `/duplicate`, `/compare`, `/export`, `/delete`, `/restore`; `maps.go:41`, `:68`, `:86`, `:223`, `:241`. |

Пустая карта создаётся с центральной темой. Пять шаблонов `brainstorm`, `study`, `decision`, `project`, `document` создают заранее определённые редактируемые ветви без обращения к модели (`pkg/mem/mind_map_workbench.go:39`, `:57`). Например, «изучение» предлагает ключевые понятия, факты, примеры, проверочные вопросы и источники. Это каркас для работы, а не готовое содержательное извлечение из документа. В интегрированном UI шаблон выбирается при создании (`internal/webapp/assets/app.js:187`).

Новая карта по источникам — отдельная существенная реализация. POST `/maps/from-sources` принимает IDs документов, название, пользовательский акцент и подробность. `webMapDocumentPins` выбирает полное допустимое содержимое каждого выбранного документа в одной транзакции, проверяет provenance и не подменяет превышение лимита скрытой выборкой первых фрагментов (`pkg/mem/web_map_from_sources.go:32`). Создание корня и фоновой задачи атомарно (`:205`). Краткий/стандартный/подробный уровни являются инструкцией модели, а не жёсткой гарантией формы результата (`:125`).

Этот сценарий автоматически применяет результат только к специально созданной новой карте. Для AI-операций над существующими картами сохраняется просмотр и явное применение предложений (`pkg/mem/web_map_ai_worker.go:268`). Если публикация не прошла, готовое предложение остаётся доступным для разбора. Это полезная основа для будущего режима «предложить структуру → проверить → доработать».

## 4. AI: реализованные гарантии и главный предел качества

Ядро поддерживает `new_map`, `expand_branch`, `fill_node`, `find_sources` (`pkg/mem/mind_map_ai.go:113`). Модель возвращает предложения по строгой схеме, а IDs узлов и evidence anchors назначает программа; ссылки модели разрешаются только в переданный набор evidence. Есть проверка структуры, ограничение количества предложений, повторные запросы при ошибках формата и ограниченное увеличение token budget (`:887`, `:970`, `:1137`). Эти проверки защищают формат и привязку источников, но не доказывают, что утверждение правильно следует из цитаты.

Preview хранится отдельно от дерева. Публикация проверяет сохранённый preview, ревизию и digest карты, актуальность evidence, доступность целевого узла и блокировку (`:1587`, `:1671`, `:1720`). Выбор части предложений учитывает родительские зависимости. Расширение добавляет узлы; `fill` дописывает текст к существующему, пропуская точное/вложенное повторение, и прикрепляет источники (`:1878`, `:1907`). Это не операция незаметного переписывания ручных заметок. `find_sources` прикрепляет выбранные anchors и исключает повторы по citation/hash (`:1919`, `:1935`).

CLI имеет более широкий выбор контекста: документ, страницы, поисковый запрос, entry IDs, источники узла и явное разрешение работы без источников (`cmd/mem/mindmap_ai.go:162`). Пустой scope для `ai-new` использует активную базу в пределах разрешённого manifest. Для ветви ядро умеет искать evidence в ветви/ближайшем предке и через ссылки на knowledge nodes (`mind_map_ai.go:669`, `:715`).

В web AI контекст — direct evidence выбранной ветви плюс вручную выбранные фрагменты. `UseBranch` пропускает ссылки типа knowledge_node, URL и файлы (`pkg/mem/web_map_ai.go:144`). Интерфейс выбора дополнительных фрагментов — постраничный список по 30, без параметров поиска/фильтра документа в этом обработчике (`internal/webapp/assets/maps-ai.js:45`). Это слабое место для больших библиотек. Наличие прикреплённой ссылки на граф само по себе не означает, что web AI использовал доказательства этого объекта.

Главный структурный предел: большие наборы разбиваются на независимые пакеты, каждый содержит запрос, целевой узел/путь и свою часть evidence (`mind_map_ai.go:777`). Между пакетами не передаётся накопленная тематическая структура. `reduceClassicMindMapAIProposals` объединяет результаты; специальная дедупликация есть лишь для поиска источников (`:1240`). Для `new_map` корни следующих пакетов становятся детьми первого; для `expand_branch` предложения просто объединяются. Wizard «по источникам» использует именно expand (`web_map_from_sources.go:209`).

Следовательно, запрос «4–7 главных тем, объединить связанные идеи разных документов» (`web_map_from_sources.go:201`) не обеспечен отдельным глобальным этапом синтеза. Повторяющиеся темы и локально согласованные, но глобально неудобные ветви являются ожидаемым риском архитектуры. Это статический вывод, а не измеренный дефект конкретной модели. Для развития нужны межпакетное объединение, явные критерии покрытия и проверка структуры на реальном корпусе; число обработанных chunks не является показателем качества понимания.

Фоновые web-задачи сохраняют состояние в SQLite и переживают закрытие вкладки, пока работает mem. Worker сериализован lock-файлом, проверяет отмену и восстанавливает уже записанное готовое предложение после перезапуска (`web_map_ai_worker.go:16`, `:48`, `:70`). Незавершённая модельная генерация после аварии не является полноценным автоматическим resume всех пакетов: без committed preview задача заканчивается ошибкой с предложением нового запуска.

## 5. Редактирование, layout и навигация

Структурные операции реализованы в общем ядре: добавить узел, изменить текст/тип/блокировку, перенести к другому родителю с позицией, удалить ветвь либо сохранить детей и поднять их к родителю (`pkg/mem/mind_map.go:1246`, `:1310`, `:1361`, `:1432`). Проверяются циклы, корень, глубина и locked-узлы. Web использует обязательную ожидаемую ревизию и request ID, чтобы повтор после потери ответа не создавал дубликат изменения (`pkg/mem/web_map_edit.go:35`). При чужой правке требуется обновление, автоматического слияния текста нет.

В интегрированном UI редактирование и добавление доступны из инспектора, перенос — через выбор родителя/позиции, свойства — через отдельную форму (`internal/webapp/assets/map-actions.js:16`, `:41`). Legacy UI дополнительно поддерживает drag-and-drop переподчинение: перетаскивание узла на другой вызывает move (`classicMindMapWorkspaceHTML.html:140`). Это структурный перенос, не свободное размещение карточки по координатам.

Интегрированный layout — детерминированное горизонтальное дерево с фиксированным шагом глубины и вертикальной раскладкой листьев (`internal/webapp/assets/map-layout.js:21`). Реализованы сворачивание ветвей, выбор глубины, раскрытие пути к найденному узлу, breadcrumbs, обзор всей карты, pan, fullscreen и масштаб 5–200% (`assets/app.js:156`, `:312`, `:350`). Поиск использует подстроку в label/summary/body с нормализацией регистра и «ё» (`map-layout.js:37`), а не semantic search.

Есть базовая клавиатурная доступность узлов и aria-expanded, Enter/Space и стрелки для ветвей (`assets/app.js:176`); ширина инспектора сохраняется локально и регулируется клавиатурой (`map-resize.js:4`, `:22`). В legacy редакторе есть `/` для поиска, Insert для дочернего узла и Ctrl/Cmd+S (`classicMindMapWorkspaceHTML.html:185`). Эти обработчики не заменяют полноценную проверку accessibility реальным screen reader.

В проверенном коде нет радиальной/двусторонней/fishbone-раскладки, свободных координат, режима презентации и пользовательских cross-links. Состояние сворачивания и масштаба интегрированного редактора хранится в текущем `state.map`, а не как сохраняемый вид карты (`assets/app.js:122`). Текст `body_markdown` в инспекторе выводится как текст; наличие поля Markdown не означает встроенный rich-text/формульный редактор. Для больших карт поэтому важнее развивать навигацию и сохранённые виды, чем просто увеличивать максимальное число узлов.

## 6. Источники, чтение документа и ограничения provenance

Четыре вида источников — evidence, внешний файл, URL, knowledge node (`pkg/mem/mind_map.go:72`). Можно прикреплять, удалять и переставлять источники; операции входят в историю. Локальный поиск evidence использует lexical scores и текстовое совпадение, фильтры документа/страницы; это не вызов embedding-модели (`mind_map_sources.go:350`). URL допускаются только http/https (`:639`), сохранение ссылки не скачивает сайт и не проверяет его утверждения.

Direct evidence привязано к конкретной ревизии и сохранённому excerpt. После изменения документа источник становится stale/missing; новый текст не подставляется как будто это прежняя цитата. Чтение документа проверяет соответствие document/revision/page/block/hash/path и фрагмента текущим entries (`pkg/mem/web_map_document.go:30`). Для stale возвращается сохранённая цитата с предупреждением. При наличии страницы показываются её chunks; без страницы — соседние блоки. Ограничения объёма приводят к показу цитаты вместо огромного контекста (`:66`, `:111`).

В интегрированном UI есть сопоставление текста узла и passage документа, а также открытие проверенного оригинала PDF на странице (`internal/webapp/assets/map-document.js`; `web_map_document.go:149`). Перед отдачей оригинала проверяются путь и fingerprint; hosted-доступ ограничен собственным корнем. Но это ещё не полноценная читалка с пометками на страницах, выделением произвольного диапазона и двусторонним индексом всех заметок документа. PNG-crop формул из knowledge graph нельзя засчитывать как реализованный preview классического редактора.

Web-вложения хранятся как immutable BLOB с digest внутри SQLite, атомарно с source/history, поэтому undo не теряет файл (`pkg/mem/web_map_attachments.go:16`). Прежний локальный импорт вложений использует приватное файловое хранение и другой предел размера (`mind_map_sources.go:772`). Интегрированный UI помечает локальные ссылки старого формата как открываемые в прежнем редакторе (`assets/map-library.js:62`). При экспорте карты сохраняется описание источников, однако это не архив всех внешних файлов; перенос всей базы — отдельная функция portable database.

## 7. Вопросы по ветви, карточки и сравнение

Вопрос по ветви сначала строит manifest выбранного поддерева и текущих evidence. Ответ обязан опираться на этот набор, проверяется после модели; web дополнительно повторно проверяет manifest перед отдачей ответа (`pkg/mem/mind_map_workbench.go:134`, `:196`; `web_map_workbench.go:181`). Stale/missing исключаются из основания. И core branch Q&A, и web branch Q&A используют прямые evidence; более богатый resolver AI-редактирования через knowledge nodes здесь не применяется (`mind_map_workbench.go:639`; `web_map_workbench.go:82`). Поэтому функция отвечает по подтверждениям ветви, а не автоматически по всей библиотеке или содержимому всех URL.

Учебные карточки создаются детерминированно: вопрос из label, ответ из summary/body, при пустом тексте — названия детей; пустые листья пропускаются (`mind_map_workbench.go:280`). Это быстрый просмотр уже написанного материала. Нет отдельного AI-этапа генерации качественных проверочных вопросов, классификации трудности и проверки ответа учащегося.

Web позволяет переворачивать карточку, переходить вперёд/назад, открыть её узел, скачать Markdown и отметить изученной. Однако `known: new Set()` создаётся при каждом открытии диалога (`internal/webapp/assets/map-workbench.js:14`, `:42`). Прогресс не сохраняется между открытиями. Нет долговременных оценок, расписания повторений, статистики усвоения или синхронизации с Anki в проверенных структурах и маршрутах. Для учебного продукта это отдельный слой данных, а не косметическая правка карточек.

Сравнение двух карт показывает added/removed/changed/moved/unchanged. Сопоставление начинается с нормализованных путей названий, затем ищет перенос по сигнатуре (`mind_map_workbench.go:363`, `:465`). Это полезно для двух ручных версий или результатов разных генераций, но не является семантическим diff документов: переименование может выглядеть как удаление/добавление; эквивалентность разных формулировок не устанавливается. Нет автоматического merge выбранных различий.

## 8. История, снимки, библиотека и экспорт

Каждая нормальная мутация сохраняет before/after, digest, автора и действие. Undo/redo реализованы в ядре и web; повтор запроса идемпотентен, устаревшая ревизия или разошедшаяся история отклоняются (`pkg/mem/mind_map.go:1597`, `:1633`, `:1746`; `web_map_history.go`; `web_map_redo_test.go:72`). Web-история отдаёт ограниченную метаинформацию и цели изменений, а не все внутренние snapshot JSON/пути (`web_map_history.go:73`).

Снимок фиксирует полное состояние без изменения дерева, хранит причину и ревизию (`mind_map.go:1861`). CLI и оба UI позволяют создать и перечислить снимки. Но в проверенных dispatch/routes и UI отсутствуют получение содержимого выбранного снимка для просмотра и команда «восстановить этот снимок». Web `/maps/{id}/restore` восстанавливает карту из корзины, не её историческую версию (`internal/webapp/maps.go:41`; `pkg/mem/web_map_delete.go:128`). Эти два сценария необходимо различать в будущих требованиях.

Интегрированная библиотека поддерживает metadata, дублирование, мягкое удаление и восстановление. Удаление карты сохраняет документы и историю и отменяет связанные активные AI-задачи; восстановление не возобновляет отменённую генерацию (`web_map_delete.go:21`, `:99`, `:128`). Независимая копия удобна для эксперимента, но не является branch/merge workflow.

Экспорт реализован в восьми форматах (`pkg/mem/mind_map_export.go:30`): автономный HTML, SVG, PNG, JSON, OPML, Markdown, Mermaid, Obsidian. Экспортируется полное дерево независимо от свёрнутого экранного состояния, с проверками revision/digest/state и metadata provenance (`:111`; `pkg/mem/web_map_manage.go:33`). Hosted-экспорт убирает локальные filesystem locators (`:48`).

Obsidian — один Markdown-файл с YAML, Mermaid, полным содержимым и block IDs (`mind_map_export.go:290`), не готовый многозаметочный vault. Mermaid передаёт дерево, а provenance дополнительно записан в комментарий. OPML имеет собственные расширения metadata. Это хорошие форматы отдачи, но обратный путь не реализован в проверенных пользовательских командах/API. Метод `ImportClassicMindMap` принимает внутренний draft и используется программой; его наличие не означает импорт пользовательского JSON/OPML (`mind_map.go:413`; `cmd/mem/mindmap.go:18`). PDF, XMind и FreeMind отсутствуют в enum экспорта; проверка совместимости реальными сторонними приложениями в этой задаче не проводилась.

Ограничения явно полезны для безопасности и предсказуемости alpha, но для постоянной базы документов наиболее заметны накопительные 1000 receipts и различие 10 000 core / 1000 web. До увеличения лимитов нужны измерения времени, памяти и удобства; автоматическое удаление истории ради обхода квоты не следует вводить без отдельного продуктового решения.

Есть также JS-проверки layout, source progress, document view, resize и удаления в `internal/webapp/*_test.cjs`; они не являются доказательством визуальной или screen-reader приёмки. Для текущего исследования не выполнены browser E2E, реальные импорты книг, замеры больших карт, тесты моделей и round-trip через сторонние редакторы.

При дальнейшем проектировании приоритетны: единая политика evidence для CLI и обоих UI; глобальная структура и покрытие после пакетной генерации; удобный выбор источников в большой библиотеке; сохраняемый учебный прогресс; просмотр/восстановление снимка; обратный импорт экспортируемых карт; долговременная политика квот. Поперечные связи, несколько layout и richer notes полезно описать отдельными решениями модели, не смешивая классическое дерево с существующим knowledge graph.
