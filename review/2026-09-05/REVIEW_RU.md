# Ревью mem-tool — 5 сентября 2026

Проверен текущий checkout `codex/stabilization-stage-0`, commit `63fd134b3df548c802927eaf4af1053629decaa9`, версия `1.70.3`. Исходное рабочее дерево было чистым. Ревью выявило **8 воспроизводимых дефектов: 6 уровня P2 и 2 уровня P3**. Это ошибки актуальности данных, поиска, конкурентной работы и граничных условий; критическую уязвимость или массовую порчу базы в проверенных сценариях не подтвердил.

Рабочий код, номер версии, установленные программы и пользовательские базы не изменены. Добавлены только материалы этой папки. Исправления приложения, коммит, push и развёртывание не выполнялись.

## Подтверждённые проблемы

### R1 · P2 · mem-index оставляет устаревший вектор актуальным после изменения файла

Место: `pkg/fileindex/scan.go:205–211`; связанные проверки — `141–144`, перенос аннотации — `163–168`.

Сценарий: файл ранее получил аннотацию и embedding; его содержимое изменилось; выполняется обычный `mem-index scan` без обогащения и embeddings. Сканер записывает новые `size/mtime`, но переносит прежнюю аннотацию, вектор и `EmbeddingSpace`. Следующий `scan -embed` видит совпадающие метаданные и пространство модели и пропускает файл. Изменённый документ продолжает находиться по прежнему содержимому.

Воспроизведение: `TestReviewScanInvalidatesChangedContentVector` создаёт изменённый файл и предыдущую индексную запись. После сканирования подтверждены новые метаданные вместе со старой аннотацией и вектором, отмеченным актуальным.

Исправление: отделить актуальность извлечённого содержимого и вектора от времени последнего обнаружения файла. При изменении содержимого инвалидировать производные данные; сохранять старые значения для диагностики можно, но они не должны удовлетворять условию `vectorCurrent`. При следующем обогащении нужна новая аннотация, затем embedding по ней. Проверять последовательность «enrich → изменение → scan → scan -embed», а также неудачное повторное извлечение.

### R2 · P2 · старая цитата открывает новое содержимое PDF без проверки версии файла

Место: `pkg/mem/graph_live.go:1346–1363`; разрешение цитаты — `pkg/mem/graph_source.go:20–61`. Похожая граница есть у evidence-источников классической карты в `pkg/mem/mind_map_sources.go:792–811`.

Сценарий: документ проиндексирован, в графе сохранена цитата; PDF по тому же пути затем заменён или отредактирован без повторного импорта. Проверка `EvidenceCurrent` сравнивает сохранённые записи БД. После неё HTTP-обработчик открывает текущее содержимое пути и отдаёт его как источник прежней цитаты. В новой редакции PDF текст и номера страниц могут уже отличаться. Аналогичный риск возникает после восстановления старой индексной версии при оставленном новом файле.

Воспроизведение: `TestReviewSourceDoesNotServeChangedPDF` заменяет файл уже существующего тестового источника. Запрос по прежнему `citation_id` получает **HTTP 200 и байты нового документа**.

Исправление: при импорте сохранять отдельный отпечаток физического файла либо неизменяемую копию оригинала. Проверять открытый файл перед выдачей; при несовпадении объяснять, что источник изменён. Текущий `DocumentRevision` нельзя просто сравнить с SHA-256 PDF: `ingest.ContentRevision` вычисляется по извлечённым блокам и сведениям о страницах. Для старых баз потребуется явное состояние неизвестного отпечатка или повторный импорт.

Ограничение проверки: использован существующий HTTP fixture репозитория, без визуального открытия настоящего PDF; подтверждена именно выдача изменённых байтов по старой ссылке.

### R3 · P2 · исключённые фильтром записи меняют оценку оставшихся результатов поиска

Место: `pkg/mem/search.go:109–113`; фильтрация кандидатов — `84–88`.

Лексические оценки собираются по всей базе. Кандидаты затем фильтруются по backend, тегам и датам, однако решение о смешивании векторной и лексической оценок опирается на исходный `len(lexicalScores)`. Совпадение только в исключённой записи включает смешивание 50/50 для оставшихся записей, у которых лексических совпадений нет.

Воспроизведение: `TestReviewFilteredSearchIgnoresExcludedLexicalHits`. Для неизменных запроса, вектора и фильтра `Tags=[keep]` добавление записи с тегом `excluded` меняет оценку единственного допустимого результата **с 1 до 0.5**. При пороге релевантности полезный результат может исчезнуть. Ошибка затрагивает общий поисковый слой, используемый CLI и подбором контекста.

Исправление: определять наличие лексических совпадений по допустимым кандидатам. Проверить также область нормализации лексических оценок, чтобы фильтр и порог имели понятную согласованную семантику. Дополнить проверками для тегов, backend и дат.

### R4 · P2 · краткая блокировка SQLite немедленно срывает запись из другого Store

Место: `pkg/mem/store.go:235–241`, запись — `707–713`. Аналогичная политика открытия без настройки ожидания присутствует в `pkg/fileindex/store.go:101`.

`sync.Mutex` защищает один экземпляр Store. У подключений SQLite не настроены ожидание занятого writer и ограниченный повтор операции. Поэтому параллельные CLI/live-процессы могут немедленно получать `database is locked`, хотя первая транзакция скоро завершится.

Воспроизведение: `TestReviewSQLiteWaitsForShortExternalWrite` открывает два Store одной временной базы. Первый удерживает короткую транзакцию 100 мс. `Add` во втором получает **SQLITE_BUSY (5)** сразу, до освобождения блокировки. Частично сохранённая запись этим тестом не обнаружена; проблема — отказ нормальной операции при кратком пересечении транзакций.

Исправление: задать ограниченный `busy_timeout` для каждого нового соединения и политику повторов транзакций. Настройка только одного произвольного соединения из пула недостаточна. Отдельно проверить BEGIN/read-to-write/COMMIT, отмену и длительную блокировку. WAL может снизить конкуренцию чтения с записью, но не заменяет обработку единственного writer.

### R5 · P2 · fixed-разбиение добавляет лишний хвостовой чанк

Место: `pkg/mem/chunk.go:302–307`.

После записи чанка, достигшего конца текста, цикл снова вычисляет `end - overlap`. При положительном overlap и подходящей длине текста следующая итерация создаёт фрагмент, полностью содержащийся в предыдущем. Это лишние embedding-запросы, записи в базе и повторяющийся материал при поиске. Через общий `ChunkDocument` ошибка затрагивает импорт и индексацию при стратегии `fixed`.

Воспроизведение: `TestReviewFixedChunkStopsAtEnd`: `ChunkDocument("0123456789", 100, 2, "fixed")` возвращает `"0123456789"` и **лишний `"89"`**, хотя весь текст помещается в один чанк.

Исправление: завершать цикл сразу после добавления чанка с `end == len(runes)`. Проверить короткий текст, точную границу размера, Unicode и перекрытие нескольких полноценных чанков.

### R6 · P2 · явно выбранный каталог с точкой в имени индексируется как пустой

Место: `pkg/mem/indexer.go:64–67`.

Правило пропуска скрытых папок применяется и к самому корню обхода. Поэтому `mem index <путь к .notes>` завершается успешно с нулём файлов, даже если пользователь явно выбрал каталог с поддерживаемыми документами. В `fileindex.Scan` аналогичный случай уже обработан исключением для корня.

Воспроизведение: `TestReviewIndexExplicitHiddenRoot` создаёт `.notes/empty.txt`. Получены `0 файлов, 0 чанков`, ошибка отсутствует. Пустой текст выбран, чтобы тест не зависел от embedding-провайдера; файл всё равно должен попасть в результаты обработки.

Исправление: применять пропуск только к вложенным каталогам, сравнивая `path` с каноническим корнем. Рядом, в `61–62`, ошибки обхода файловой системы безусловно подавляются — их также нужно включать в отчёт об индексации. Последняя проблема установлена по коду, отдельный сценарий отказа в доступе не воспроизводился.

### R7 · P3 · paragraph-разбиение иногда превышает max_size на один символ

Место: `pkg/mem/chunk.go:158`, фактический разделитель — `170–172`.

Проверка вместимости учитывает один символ между абзацами, а запись добавляет два перевода строки. `TestReviewParagraphRespectsMaxSize` показывает: `"12345\n\n6789"` при `max_size=10` превращается в чанк длиной **11** символов. Нарушается заявленный предел размера, хотя величина превышения мала.

Исправление: учитывать фактическую длину разделителя и проверять конечные длины в символах для всех стратегий.

### R8 · P3 · фильтр -to исключает дробную часть последней секунды дня

Место: `pkg/mem/search.go:198–201`.

Верхняя граница вычисляется как полночь плюс сутки минус одна секунда. Записи сохраняются с точностью `RFC3339Nano`, поэтому часть последней секунды выпадает из диапазона.

Воспроизведение: `TestReviewDateIncludesEntireLastDay`: запись `2026-09-05T23:59:59.500Z` не проходит `-to 2026-09-05`.

Исправление: использовать полуоткрытый интервал до начала следующего дня: исключать `t >= nextDay`, сохраняя все времена до него. Это исправление не требует попутной смены принятой часовой зоны фильтра.

## Что улучшить после исправления ошибок

Это предложения по устройству проекта, а не дополнительные доказанные отказы.

1. **Сократить полные перестроения поисковых данных.** `Store.add`/`DeleteById` меняют кэш, но оставляют старый `entryGeneration`, поэтому следующее чтение перечитывает корпус. `rebuildFTSTx` удаляет и заново вставляет весь FTS-индекс. Для крупных баз полезны атомарное обновление generation и изменения FTS только для затронутых строк. Сначала нужен замер на репрезентативном корпусе и сохранение существующих межпроцессных гарантий.
2. **Ускорить fileindex без изменения поисковой семантики.** `GetByPath` и обновление кэша в `Upsert` линейно обходят `s.files`. Повторный обход большой папки превращается в множество линейных поисков. Индекс path → позиция и ID → позиция устранит эту часть затрат.
3. **Разделить код CLI и браузерных приложений.** В `cmd/mem/main.go` около 188 КБ; `graph_view.go` — около 298 КБ, `mind_map_view.go` — около 137 КБ. Большие HTML/CSS/JS-строки затрудняют локальное ревью и диагностику. Вынос статических ресурсов через `go:embed` и разделение CLI по областям дадут более удобные места для правок. Существующие проверки синтаксиса JS сохранить; добавить реальные пользовательские браузерные сценарии, когда доступ разрешён.
4. **Унифицировать импорт.** `add-file`, `index` и `import` используют разные пути чтения/разбиения/provenance. Текстовые файлы читаются целиком, а `MarkdownExtractor.Extract` игнорирует context. Нужны согласованные ограничения размеров и отмена до дорогой обработки, с понятной политикой для больших корпусов. Без замера не заявляю конкретную величину перерасхода памяти.
5. **Уточнить поведение незавершённых функций.** Telegram `/import` предлагает прислать файл, но реализован как сообщение «пока в разработке»; обработчик обычных updates не индексирует документы. Лучше прямо показывать доступный способ импорта или скрыть обещание до реализации. Живая отправка сообщений в Telegram в этом ревью не выполнялась.
6. **Сохранить резервные бинарники при неудачном rollback.** `deploy/windows.ps1` сообщает о неполном восстановлении, но внешний `finally` всё равно вызывает `Remove-Stage`, удаляющий `previous-*`. При таком отказе резервные файлы следует оставлять с явным путём для ручного восстановления. Вывод по управлению потоком скрипта, без аварийного испытания установленного комплекта.

## Воспроизведение и порядок исправления

Из корня репозитория:

```powershell
./review/2026-09-05/run-probes.ps1
```

Скрипт через Go `-overlay` подключает `mem_probes.go.txt` и `fileindex_probes.go.txt` как временные тестовые файлы соответствующих пакетов. Производственные исходники не меняются. Все базы и проверяемые источники создаются в `t.TempDir`. Код выхода 1 сейчас ожидаем: проверки выражают правильное поведение и падают на найденных ошибках. Вывод — `probe-results.txt`. Обычный `go test ./...` эти диагностические файлы не подхватывает.

Рекомендуемый порядок работ:

1. R1–R3: актуальность аннотаций/векторов, связь цитаты с физическим источником, влияние фильтров на поиск.
2. R4: политика ожидания SQLite и проверки параллельных процессов.
3. R5–R8: граничные условия разбиения, обход каталогов и даты.
4. Перенести проверки исправленных дефектов в штатные тесты; затем полный test/vet, Linux race и браузерные действия на изолированной базе.
5. Определить SemVer по окончательному объёму изменений, обновить release notes и USAGE_RU при изменении поведения CLI; выпускать все три бинарника штатным `deploy/windows.ps1`. Текущее ревью само по себе выпуска не требует.
